# 6.4 Inheritance

## Overview

Inheritance lets a class (the subclass, or child) reuse and extend the behaviour of another class (the base class, superclass, or parent). It models an "is-a" relationship: a `Dog` is an `Animal`. Used well, it removes duplication and allows different classes to be used interchangeably. Used carelessly, it creates tangled hierarchies that are hard to change.

## Single Inheritance

Put the parent class in parentheses after the class name.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound"

    def describe(self):
        return f"{self.name} is an animal"


class Dog(Animal):
    def speak(self):                     # overrides the parent's method
        return f"{self.name} barks"


class Cat(Animal):
    def speak(self):
        return f"{self.name} meows"


animals = [Dog("Rex"), Cat("Tom"), Animal("Thing")]
for animal in animals:
    print(animal.speak())
# Rex barks
# Tom meows
# Thing makes a sound

print(Dog("Rex").describe())       # Rex is an animal, inherited unchanged
```

`Dog` and `Cat` inherit `__init__` and `describe`, and replace `speak`. Code that works with an `Animal` works with either subclass, a property called polymorphism.

Useful checks:

```python
rex = Dog("Rex")
print(isinstance(rex, Dog))        # True
print(isinstance(rex, Animal))     # True: a Dog is an Animal
print(issubclass(Dog, Animal))     # True
print(type(rex) is Animal)         # False
```

Every class inherits from `object` implicitly.

## super()

`super()` gives access to the parent's version of a method, so a subclass can extend behaviour instead of replacing it. The most common use is calling the parent's `__init__`.

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def annual_cost(self):
        return self.salary * 12


class Manager(Employee):
    def __init__(self, name, salary, team):
        super().__init__(name, salary)        # let Employee set up name and salary
        self.team = team

    def annual_cost(self):
        return super().annual_cost() + 5000   # extend, do not rewrite


m = Manager("Amina", 4000, ["Bilal", "Chen"])
print(m.annual_cost())      # 53000
```

If a subclass defines `__init__` and forgets `super().__init__`, the parent's attributes are never created.

## Method Overriding

A subclass method with the same name replaces the inherited one for instances of the subclass. Follow the Liskov substitution principle: a subclass should accept at least what the parent accepts and return what callers of the parent expect, so a subclass instance can be used wherever the parent is expected. An override that raises errors for inputs the parent handled breaks that promise.

## Multiple Inheritance

A class can inherit from several parents.

```python
class Flyer:
    def move(self):
        return "flying"


class Swimmer:
    def move(self):
        return "swimming"


class Duck(Flyer, Swimmer):
    pass


print(Duck().move())      # flying, Flyer comes first
```

When several parents define the same name, Python needs a clear rule to choose.

## Method Resolution Order (MRO)

The MRO is the ordered list of classes Python searches when looking up an attribute. It is computed with the C3 linearization algorithm, which guarantees that a class comes before its parents and that the order of the parents you listed is preserved.

```python
print(Duck.__mro__)
# (<class 'Duck'>, <class 'Flyer'>, <class 'Swimmer'>, <class 'object'>)
print([cls.__name__ for cls in Duck.mro()])
```

`super()` does not mean "my parent". It means "the next class in the MRO of the instance". That is what makes cooperative multiple inheritance work, as the diamond shows.

```python
class A:
    def hello(self):
        return "A"


class B(A):
    def hello(self):
        return "B" + super().hello()


class C(A):
    def hello(self):
        return "C" + super().hello()


class D(B, C):
    def hello(self):
        return "D" + super().hello()


print(D().hello())                          # DBCA
print([c.__name__ for c in D.__mro__])      # ['D', 'B', 'C', 'A', 'object']
```

Each class appears once in the MRO, and `A.hello` runs only once even though both `B` and `C` inherit from `A`. If a class hierarchy has an impossible ordering, Python raises `TypeError: Cannot create a consistent method resolution order`.

For multiple inheritance to work, every method involved should call `super()`, and constructors should accept and pass along `*args` and `**kwargs`.

## Mixins

A mixin is a small class that adds one focused behaviour to other classes. It is not meant to be instantiated on its own and usually holds no data of its own.

```python
import json


class JsonMixin:
    def to_json(self):
        return json.dumps(self.__dict__)


class TimestampMixin:
    def touch(self):
        import time
        self.updated_at = time.time()


class Product(JsonMixin, TimestampMixin):
    def __init__(self, name, price):
        self.name = name
        self.price = price


p = Product("Pen", 2)
print(p.to_json())       # {"name": "Pen", "price": 2}
```

Guidelines for mixins:

- One clear responsibility.
- Name them `...Mixin`.
- List mixins before the main base class so their methods take priority.
- Use `super()` so they cooperate with the rest of the chain.

## When Inheritance Goes Wrong

- Deep hierarchies (more than two or three levels) are hard to understand, because behaviour is spread across many files.
- A subclass that overrides most of its parent's methods probably should not inherit from it.
- A change to a base class can silently break every subclass. This is called the fragile base class problem.
- Inheriting just to reuse code, when the "is-a" relationship is not true, produces confusing designs.

## Basic Examples

```python
class Shape:
    def __init__(self, name):
        self.name = name

    def area(self):
        return 0

    def __repr__(self):
        return f"{self.name}(area={self.area():.2f})"


class Rectangle(Shape):
    def __init__(self, width, height):
        super().__init__("Rectangle")
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height


class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side)
        self.name = "Square"


shapes = [Rectangle(2, 3), Square(4)]
print(shapes)                       # [Rectangle(area=6.00), Square(area=16.00)]
print(sum(s.area() for s in shapes))   # 22
```

## Backend Industry Example

A notification system. The base class defines the shared workflow (validate, then deliver) and each subclass supplies only the delivery step. An audit mixin adds record-keeping to any notifier without changing it, and `super()` lets the pieces cooperate.

```python
class Notifier:
    """Base class: validates a message, then delegates delivery to subclasses."""

    def send(self, recipient: str, message: str) -> str:
        if not message.strip():
            raise ValueError("message must not be empty")
        return self.deliver(recipient, message)

    def deliver(self, recipient: str, message: str) -> str:
        raise NotImplementedError("subclasses must implement deliver()")


class EmailNotifier(Notifier):
    def deliver(self, recipient: str, message: str) -> str:
        return f"email to {recipient}: {message}"


class SmsNotifier(Notifier):
    MAX_LENGTH = 160

    def deliver(self, recipient: str, message: str) -> str:
        return f"sms to {recipient}: {message[: self.MAX_LENGTH]}"


class AuditMixin:
    """Record every send in an audit trail. Must come before a Notifier in the bases."""

    def __init__(self, *args, **kwargs) -> None:
        super().__init__(*args, **kwargs)
        self.audit_trail: list[str] = []

    def send(self, recipient: str, message: str) -> str:
        result = super().send(recipient, message)
        self.audit_trail.append(f"sent to {recipient}")
        return result


class AuditedSmsNotifier(AuditMixin, SmsNotifier):
    pass


notifiers: list[Notifier] = [EmailNotifier(), SmsNotifier(), AuditedSmsNotifier()]
for notifier in notifiers:
    print(notifier.send("+8801700000000", "Your order has shipped"))

audited = notifiers[2]
print(audited.audit_trail)                 # ['sent to +8801700000000']
print([cls.__name__ for cls in AuditedSmsNotifier.__mro__])
# ['AuditedSmsNotifier', 'AuditMixin', 'SmsNotifier', 'Notifier', 'object']

try:
    EmailNotifier().send("a@example.com", "   ")
except ValueError as exc:
    print(exc)                             # message must not be empty
```

The calling code treats every notifier the same way through `send`. The base class owns the rule that messages cannot be empty, so no subclass can forget it, and adding a push-notification channel means writing one `deliver` method. `AuditMixin.send` calls `super().send`, which according to the MRO is `SmsNotifier`'s inherited `Notifier.send`. The behaviours combine without either class knowing about the other.

## Common Mistakes

- Forgetting to call `super().__init__()` in a subclass constructor.
- Believing `super()` always means the direct parent, which is wrong with multiple inheritance.
- Building deep class hierarchies for code reuse alone.
- Using inheritance when the relationship is "has-a" and not "is-a".
- Overriding a method in a way that breaks what the parent promised.
- Making a subclass depend on the internal details of its parent.
- Writing mixins that hold state or depend on specific classes.

## Summary

Inheritance lets a subclass reuse and specialize a parent class through overriding and `super()`. Multiple inheritance follows the method resolution order, which you can inspect with `__mro__`, and mixins add one focused behaviour. Use inheritance for true "is-a" relationships with shallow hierarchies, call `super()` consistently, and keep subclasses substitutable for their parents.
