# 6.9 Encapsulation Conventions

## Overview

Encapsulation means keeping an object's internal details hidden behind a small public interface, so the inside can change without breaking the people using it. Python does not have `private` or `protected` keywords. Instead it relies on naming conventions and a few mechanisms. The common saying is that "we are all consenting adults": the language trusts you to respect the signals instead of enforcing them.

## Public, Protected, and Private Names

| Name style | Meaning | Example |
| --- | --- | --- |
| `name` | Public. Part of the interface. Safe to use and to rely on. | `account.balance` |
| `_name` | Internal ("protected"). Not part of the interface. May change without notice. | `account._ledger` |
| `__name` | Name-mangled. Prevents clashes in subclasses. | `account.__audit_log` |
| `__name__` | Reserved for Python itself. Do not invent your own. | `__init__`, `__repr__` |

### Single Underscore: `_internal`

A leading underscore tells readers "this is an implementation detail". Python does not stop anyone from using it, but code outside the class that touches `_ledger` is taking responsibility for breakage. Linters flag such access.

```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner                # public
        self._balance = balance           # internal

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

    @property
    def balance(self):                    # public, read-only view
        return self._balance
```

At module level, names beginning with an underscore are skipped by `from module import *`. It is also the usual way to mark helper functions as internal.

### Double Underscore: Name Mangling

Inside a class body, an attribute named `__x` is renamed by Python to `_ClassName__x`.

```python
class Account:
    def __init__(self):
        self.__secret = 42


a = Account()
print(a.__secret)             # AttributeError
print(a._Account__secret)     # 42, still reachable
print(vars(a))                # {'_Account__secret': 42}
```

The purpose is to avoid accidental name clashes between a class and its subclasses, not to provide security. Anyone can still read `_Account__secret`.

```python
class Base:
    def __init__(self):
        self.__id = "base"         # stored as _Base__id


class Child(Base):
    def __init__(self):
        super().__init__()
        self.__id = "child"        # stored as _Child__id, does not overwrite Base's


c = Child()
print(vars(c))                     # {'_Base__id': 'base', '_Child__id': 'child'}
```

Use mangling rarely, in base classes designed to be subclassed by people you do not control. For everything else, a single underscore is the convention.

## Controlling Access with Properties

When access needs rules, use a property: the attribute looks public while validation and read-only behaviour stay hidden.

```python
class Thermostat:
    def __init__(self, target):
        self._target = target

    @property
    def target(self):
        return self._target

    @target.setter
    def target(self, value):
        if not 5 <= value <= 30:
            raise ValueError("target must be between 5 and 30")
        self._target = value
```

## `__slots__`

By default every instance stores its attributes in a dictionary (`__dict__`). `__slots__` declares the exact attribute names a class may have and replaces the dictionary with a compact fixed layout.

```python
class LogEvent:
    __slots__ = ("timestamp", "level", "message")

    def __init__(self, timestamp, level, message):
        self.timestamp = timestamp
        self.level = level
        self.message = message


event = LogEvent(1700000000.0, "INFO", "started")
event.extra = "nope"
# AttributeError: 'LogEvent' object has no attribute 'extra'
print(hasattr(event, "__dict__"))     # False
```

Benefits:

- Lower memory use per instance, which matters when creating millions of small objects.
- Slightly faster attribute access.
- Misspelled attribute names raise an error instead of silently creating a new attribute.

Costs and rules:

- Instances cannot receive attributes that are not listed in `__slots__`.
- A name in `__slots__` cannot also be a class attribute with a default value (`ValueError: 'x' in __slots__ conflicts with class variable`). Set defaults in `__init__`.
- Instances cannot be weakly referenced unless `"__weakref__"` is in the slots.
- Subclasses that do not define `__slots__` get a `__dict__` again, which removes the benefit.
- Multiple inheritance from several classes that each define non-empty slots is not allowed.

Dataclasses offer the same layout with `@dataclass(slots=True)`.

Measuring the difference:

```python
import tracemalloc


class Plain:
    def __init__(self, a, b):
        self.a = a
        self.b = b


class Slotted:
    __slots__ = ("a", "b")

    def __init__(self, a, b):
        self.a = a
        self.b = b


def memory_for(cls, count=100_000):
    tracemalloc.start()
    objects = [cls(1, 2) for _ in range(count)]
    used, _ = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    return used


print(memory_for(Plain), memory_for(Slotted))    # the slotted version is smaller
```

## What Encapsulation Is and Is Not

- It is about stable interfaces, not secrecy. Never rely on underscores or mangling to protect a secret. Anything in memory can be read.
- Document the public interface and keep it small. Everything public is a promise to callers.
- Do not expose mutable internals. A method that returns `self._items` lets callers change your list. Return a copy or a tuple instead.

```python
class Cart:
    def __init__(self):
        self._items = []

    def add(self, item):
        self._items.append(item)

    @property
    def items(self):
        return tuple(self._items)       # callers get a snapshot, not the internal list
```

## Basic Examples

```python
class BankAccount:
    def __init__(self, owner, opening_balance=0):
        self.owner = owner
        self._balance = opening_balance
        self._history = []

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        self._record("deposit", amount)
        self._balance += amount

    def _record(self, kind, amount):          # internal helper
        self._history.append((kind, amount))

    def statement(self):
        return list(self._history)             # a copy, the internal list stays private


acct = BankAccount("Amina", 100)
acct.deposit(50)
print(acct.balance)       # 150
print(acct.statement())   # [('deposit', 50)]
```

## Backend Industry Example

An API client whose token and header construction are internal, whose `repr` never reveals the secret, and a high-volume event object that uses `__slots__`.

```python
class ApiClient:
    """Builds authenticated requests for an external service."""

    def __init__(self, base_url: str, token: str, timeout: float = 5.0) -> None:
        self.base_url = base_url.rstrip("/")        # public configuration
        self.timeout = timeout
        self._token = token                          # internal, never exposed

    def _headers(self) -> dict[str, str]:
        """Internal helper. May change without notice."""
        return {
            "Authorization": f"Bearer {self._token}",
            "Accept": "application/json",
        }

    def build_request(self, path: str) -> dict:
        """Public interface: describe a request to the given path."""
        return {
            "url": f"{self.base_url}/{path.lstrip('/')}",
            "headers": self._headers(),
            "timeout": self.timeout,
        }

    def __repr__(self) -> str:
        return f"ApiClient(base_url={self.base_url!r}, token='***')"


client = ApiClient("https://api.example.com/", token="s3cr3t-token")
print(client)                                  # ApiClient(base_url='https://api.example.com', token='***')
print(client.build_request("/orders")["url"])  # https://api.example.com/orders


class LogEvent:
    """A small object created in very large numbers, so it uses slots."""

    __slots__ = ("timestamp", "level", "message")

    def __init__(self, timestamp: float, level: str, message: str) -> None:
        self.timestamp = timestamp
        self.level = level
        self.message = message

    def __repr__(self) -> str:
        return f"LogEvent({self.timestamp}, {self.level!r}, {self.message!r})"


events = [LogEvent(1700000000.0 + i, "INFO", f"request {i}") for i in range(3)]
print(events[0])

try:
    events[0].severity = "high"            # a typo or an unplanned attribute
except AttributeError as exc:
    print(exc)                             # 'LogEvent' object has no attribute 'severity'
```

Callers use `build_request` and never need to know how authentication works. If the service later changes to signed requests, only `_headers` changes. Because `__repr__` hides the token, accidentally logging the client object does not leak the secret. The slotted event uses less memory per instance and rejects misspelled attributes.

## Common Mistakes

- Treating `_name` or `__name` as security. Neither prevents access.
- Using double underscores everywhere "to be safe", which only makes debugging and testing harder.
- Returning internal mutable objects directly from methods.
- Accessing another class's `_internal` attributes from outside.
- Adding `__slots__` to a class and then expecting to attach new attributes dynamically.
- Including a secret in `__repr__`, `__str__`, or error messages.
- Making everything public and then being unable to change anything without breaking callers.

## Summary

Python signals privacy with naming conventions. A single leading underscore marks internal details, double underscores trigger name mangling to avoid clashes in subclasses, and properties control access to public attributes. `__slots__` fixes an instance's attributes for lower memory use and stricter attribute checking, at the cost of flexibility. Keep the public interface small and stable, hide mutable internals, and never rely on any of these mechanisms to protect secrets.
