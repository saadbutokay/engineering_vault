# 6.5 Composition vs Inheritance

## Overview

There are two main ways to build a class out of other classes. Inheritance says a new class is a specialized version of an existing one (an "is-a" relationship). Composition says a new class contains other objects and uses them (a "has-a" relationship). A widely repeated design guideline is to favour composition over inheritance, because it produces more flexible and more testable code.

## "Is-a" versus "Has-a"

- A `Dog` is an `Animal`. Inheritance fits.
- A `Car` has an `Engine`. A `Car` is not an `Engine`. Composition fits.
- An `OrderService` has a payment gateway, an inventory, and a notifier. It is none of them.

A quick test: if you can say "X is a kind of Y" and every use of Y would also be valid for X, inheritance may be right. Otherwise use composition.

## Composition in Practice

```python
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower
        self.running = False

    def start(self):
        self.running = True
        return "engine started"


class Car:
    def __init__(self, engine):
        self.engine = engine           # Car has an Engine

    def start(self):
        return self.engine.start()     # delegate the work to the part


car = Car(Engine(150))
print(car.start())                     # engine started
```

The `Car` delegates to its engine. It can use any object that provides `start()`, so swapping in an `ElectricMotor` requires no changes to `Car`.

## Problems with Inheritance

Inheriting just to reuse code causes trouble.

```python
class Stack(list):               # a Stack "is a" list?
    def push(self, item):
        self.append(item)

    def peek(self):
        return self[-1]


s = Stack()
s.push(1)
s.push(2)
s.insert(0, 99)                  # allowed, but a stack must not do this
s.sort()                         # also nonsense for a stack
```

A `Stack` that inherits from `list` exposes every list operation, so callers can break its rules. Composition keeps the interface narrow.

```python
class Stack:
    def __init__(self):
        self._items = []

    def push(self, item):
        self._items.append(item)

    def pop(self):
        return self._items.pop()

    def peek(self):
        return self._items[-1]

    def __len__(self):
        return len(self._items)
```

Only the operations that make sense for a stack exist, and the internal list can later be replaced by something else without breaking any callers.

More reasons to prefer composition:

- Changing behaviour at runtime. Swap a component (a different tax calculator, a different gateway) while the program runs.
- Avoiding class explosions. With inheritance, combining three independent options yields many subclasses (`EmailAuditedRetryingNotifier`). With composition, you combine three small objects.
- Easier testing. A collaborator can be replaced by a simple fake.
- Looser coupling. The container depends only on the interface it uses and not on the parent's internal details.

## Delegation

When a class forwards a call to a component, the technique is called delegation. It can be explicit, as in `Car.start` above, or automatic through `__getattr__` for wrapper classes, but explicit is easier to read.

## Dependency Injection

Instead of creating its collaborators inside, a class receives them from outside, usually through `__init__`. This is dependency injection and it is composition's main partner.

```python
# Hard to test: the class builds its own collaborator
class ReportMailerBad:
    def __init__(self):
        self.smtp = RealSmtpClient()     # impossible to replace in a test

# Easy to test: the collaborator is injected
class ReportMailer:
    def __init__(self, smtp):
        self.smtp = smtp
```

Create real objects once, at the program's entry point, and pass them down. Tests pass fakes instead.

## When Inheritance Is Still Right

- A genuine "is-a" relationship with shared behaviour and a stable interface.
- A framework that is designed for you to subclass a base class.
- A small, shallow hierarchy where subclasses override a few methods.
- Exceptions: custom exception classes inherit from `Exception`.

A common good pattern combines both: define an interface (a base class or protocol), implement it in several classes, and have a service compose objects that satisfy that interface.

## Basic Examples

```python
class Wheel:
    def __init__(self, size):
        self.size = size


class Bicycle:
    def __init__(self):
        self.wheels = [Wheel(26), Wheel(26)]
        self.gear = 1

    def shift_up(self):
        self.gear += 1


class Logger:
    def log(self, text):
        print(f"[log] {text}")


class Calculator:
    def __init__(self, logger):
        self.logger = logger

    def add(self, a, b):
        result = a + b
        self.logger.log(f"{a} + {b} = {result}")
        return result


calc = Calculator(Logger())
calc.add(2, 3)           # [log] 2 + 3 = 5
```

## Backend Industry Example

An order service composed of three collaborators that are injected: a payment gateway, an inventory, and a notifier. Production code passes real implementations, and tests pass simple fakes. The service contains the business workflow and knows nothing about how each part works.

```python
from decimal import Decimal


class OrderService:
    def __init__(self, gateway, inventory, notifier) -> None:
        self.gateway = gateway          # any object with charge(amount, customer)
        self.inventory = inventory      # any object with reserve(...) and release(...)
        self.notifier = notifier        # any object with send(recipient, message)

    def place_order(
        self, sku: str, quantity: int, amount: Decimal, customer_email: str
    ) -> str:
        """Reserve stock, take payment, and confirm. Undo the reservation on failure."""
        if not self.inventory.reserve(sku, quantity):
            raise ValueError(f"insufficient stock for {sku}")
        try:
            receipt = self.gateway.charge(amount, customer_email)
        except ConnectionError:
            self.inventory.release(sku, quantity)
            raise
        self.notifier.send(customer_email, f"Order confirmed: {receipt}")
        return receipt


# Fakes for tests: small, fast, and fully controlled
class FakeGateway:
    def __init__(self, fail: bool = False) -> None:
        self.fail = fail
        self.charges: list[tuple[Decimal, str]] = []

    def charge(self, amount: Decimal, customer: str) -> str:
        if self.fail:
            raise ConnectionError("gateway down")
        self.charges.append((amount, customer))
        return f"receipt-{len(self.charges)}"


class InMemoryInventory:
    def __init__(self, stock: dict[str, int]) -> None:
        self.stock = dict(stock)

    def reserve(self, sku: str, quantity: int) -> bool:
        if self.stock.get(sku, 0) < quantity:
            return False
        self.stock[sku] -= quantity
        return True

    def release(self, sku: str, quantity: int) -> None:
        self.stock[sku] += quantity


class RecordingNotifier:
    def __init__(self) -> None:
        self.sent: list[tuple[str, str]] = []

    def send(self, recipient: str, message: str) -> None:
        self.sent.append((recipient, message))


# Test 1: the happy path
inventory = InMemoryInventory({"pen": 10})
notifier = RecordingNotifier()
service = OrderService(FakeGateway(), inventory, notifier)
print(service.place_order("pen", 3, Decimal("6.00"), "amina@example.com"))
print(inventory.stock, notifier.sent)
# receipt-1
# {'pen': 7} [('amina@example.com', 'Order confirmed: receipt-1')]

# Test 2: a payment failure puts the stock back and sends nothing
inventory = InMemoryInventory({"pen": 10})
notifier = RecordingNotifier()
service = OrderService(FakeGateway(fail=True), inventory, notifier)
try:
    service.place_order("pen", 3, Decimal("6.00"), "amina@example.com")
except ConnectionError as exc:
    print("failed:", exc)
print(inventory.stock, notifier.sent)     # {'pen': 10} []
```

Each collaborator can change independently. Replacing the real payment provider means writing one new class with a `charge` method. The failure scenario is tested without any network or database, which would be impractical if `OrderService` had created its own gateway, or if it had inherited from one. The service's only job is the workflow: reserve, charge, undo on failure, notify.

## Common Mistakes

- Inheriting from a class only to reuse a few of its methods.
- Inheriting from built-in containers such as `list` or `dict` and exposing operations that break the class's rules.
- Creating collaborators inside `__init__` so they cannot be replaced in tests.
- Building a class hierarchy to represent combinations of options, instead of combining small objects.
- Passing too many collaborators into one class, a sign that it does too much.
- Reaching deep into collaborators (`a.b.c.d()`) and coupling to their internal structure.

## Summary

Use inheritance for genuine "is-a" relationships and composition for "has-a" relationships. Composition gives narrow interfaces, flexible runtime behaviour, loose coupling, and easy testing. Inject collaborators through the constructor, create real ones at the program's entry point, and pass fakes in tests. When in doubt, compose.
