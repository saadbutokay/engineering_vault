# 5.7 Logging

## Overview

Logging is how a running program reports what it is doing and what went wrong. In production there is no developer watching a terminal, so logs are the main way to understand failures, performance, and behaviour after the fact. The `logging` module in the standard library is the tool for this job.

## Why print Is Not Used in Production

`print` is fine for scripts and learning. A service needs more.

- No severity. A debugging detail and a critical failure look identical.
- No timestamp, module name, or other context unless you write it yourself every time.
- No control. You cannot switch off noisy messages from one component or send errors to another destination without editing code.
- It mixes with the program's real output, which breaks tools that read standard output.
- It cannot attach a traceback or structured fields in a standard way.
- Log aggregation tools expect a consistent format that `print` does not give.

`logging` solves each of these, and it can be reconfigured without changing the code that writes the messages.

## Levels

| Level | Number | Use for |
| --- | --- | --- |
| `DEBUG` | 10 | Detailed information useful when diagnosing a problem |
| `INFO` | 20 | Normal, significant events: service started, order created |
| `WARNING` | 30 | Something unexpected happened but the program continues |
| `ERROR` | 40 | An operation failed |
| `CRITICAL` | 50 | The program cannot continue or a vital part is broken |

A logger only emits messages at or above its level. The default level is `WARNING`, so `INFO` and `DEBUG` messages are hidden until you configure it.

## A First Example

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)

logger = logging.getLogger(__name__)

logger.debug("this is hidden at INFO level")
logger.info("service started")
logger.warning("disk usage at %d percent", 91)
logger.error("could not reach payment gateway")
```

Output:

```text
2026-03-01 10:15:02,114 INFO __main__: service started
2026-03-01 10:15:02,114 WARNING __main__: disk usage at 91 percent
2026-03-01 10:15:02,114 ERROR __main__: could not reach payment gateway
```

`basicConfig` is a quick setup for small programs. It does nothing if the root logger is already configured.

## Loggers

Create one logger per module with the module's name:

```python
logger = logging.getLogger(__name__)
```

Logger names form a hierarchy separated by dots. A logger called `orders_service.payments` is a child of `orders_service`, which is a child of the root logger. Messages travel upward to the handlers of the parents (propagation), and levels can be set on any node. This lets you, for example, turn on `DEBUG` for `orders_service.payments` alone.

```python
logging.getLogger("orders_service.payments").setLevel(logging.DEBUG)
logging.getLogger("urllib3").setLevel(logging.WARNING)    # quiet a chatty library
```

## Handlers

A handler decides where records go.

| Handler | Destination |
| --- | --- |
| `StreamHandler` | a stream such as the console (standard error by default) |
| `FileHandler` | a file |
| `RotatingFileHandler` | a file that rolls over at a maximum size, keeping a number of old files |
| `TimedRotatingFileHandler` | a file that rolls over on a schedule, such as daily |
| `NullHandler` | nowhere, used by libraries |

Each handler can have its own level and formatter, so the console can show `INFO` while a file keeps `DEBUG`.

## Formatters

A formatter decides how a record looks. Useful fields:

| Field | Meaning |
| --- | --- |
| `%(asctime)s` | time of the event |
| `%(levelname)s` | level name |
| `%(name)s` | logger name |
| `%(message)s` | the message |
| `%(filename)s`, `%(lineno)d`, `%(funcName)s` | where the call was made |
| `%(process)d`, `%(threadName)s` | process and thread |

## Writing Good Log Calls

Pass values as arguments, not as an already-formatted string.

```python
logger.info("user %s placed order %s", user_id, order_id)      # recommended
logger.info(f"user {user_id} placed order {order_id}")          # avoid
```

With the first form, the string is built only if the message will actually be emitted, and log systems can group identical message templates.

Record exceptions with their traceback:

```python
try:
    charge_card(order)
except ConnectionError:
    logger.exception("payment failed for order %s", order.id)
    # ERROR level plus traceback
```

`logger.exception` should be called inside an `except` block. For another level, use `logger.warning("...", exc_info=True)`.

Add structured context with `extra`:

```python
logger.info("order created", extra={"order_id": "A-1001", "amount": "64.49"})
```

Extra keys become attributes of the record. They must not clash with built-in record attributes such as `name`, `message`, or `args`.

## What to Log, What Not to Log

- Log events with identifiers: which user, request, or order.
- Log at the point where an error is handled, not at every layer it passes through. Logging and re-raising at every level creates the same error many times.
- Never log passwords, tokens, full card numbers, or other secrets and personal data.
- Avoid logging inside very tight loops. Log summaries instead.
- Pick levels deliberately. If everything is `ERROR`, the level means nothing.

## Libraries and Applications

- A library creates loggers with `getLogger(__name__)` and never configures handlers or levels, because that is the application's decision. Libraries commonly add a `NullHandler` to their top-level logger so nothing is printed unless the application configures logging.
- An application configures logging once, at startup, in its entry point.

## Configuration with dictConfig

For anything beyond a script, describe the whole setup in a dictionary.

```python
import logging.config

LOGGING = {
    "version": 1,
    "disable_existing_loggers": False,
    "formatters": {
        "standard": {
            "format": "%(asctime)s %(levelname)s %(name)s: %(message)s",
        },
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",
            "formatter": "standard",
            "level": "INFO",
        },
        "file": {
            "class": "logging.handlers.RotatingFileHandler",
            "formatter": "standard",
            "filename": "app.log",
            "maxBytes": 5_000_000,
            "backupCount": 3,
            "encoding": "utf-8",
            "level": "DEBUG",
        },
    },
    "root": {"level": "DEBUG", "handlers": ["console", "file"]},
    "loggers": {"urllib3": {"level": "WARNING"}},
}

logging.config.dictConfig(LOGGING)
```

`disable_existing_loggers: False` keeps loggers that were created before configuration working, which is almost always what you want. The same dictionary can be loaded from a JSON or YAML configuration file, so operations teams can change logging without touching code.

## Structured Logging

Machines read logs better than people do. A log line written as JSON, with one object per line, can be searched and filtered by field in tools such as Elasticsearch, Loki, and cloud logging services. You implement this by giving the handler a custom formatter.

## Basic Examples

```python
import logging

logging.basicConfig(level=logging.DEBUG, format="%(levelname)s:%(name)s:%(message)s")
log = logging.getLogger("demo")

def divide(a, b):
    log.debug("dividing %s by %s", a, b)
    try:
        return a / b
    except ZeroDivisionError:
        log.exception("division failed")
        return None

divide(10, 2)
divide(1, 0)
```

## Backend Industry Example

A JSON formatter that includes extra fields and tracebacks, a one-function setup that writes to standard output (the usual convention for containers), and a service function that logs with context.

```python
import json
import logging
import sys
from datetime import datetime, timezone

# Attributes every LogRecord has; anything else came from `extra`
_STANDARD_ATTRIBUTES = set(vars(logging.makeLogRecord({}))) | {"message", "asctime"}


class JsonFormatter(logging.Formatter):
    """Format each log record as one line of JSON."""

    def format(self, record: logging.LogRecord) -> str:
        entry = {
            "time": datetime.fromtimestamp(record.created, tz=timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
        }
        for key, value in record.__dict__.items():
            if key not in _STANDARD_ATTRIBUTES:
                entry[key] = value                      # fields passed with extra=
        if record.exc_info:
            entry["exception"] = self.formatException(record.exc_info)
        return json.dumps(entry, default=str)


def configure_logging(level: str = "INFO", json_output: bool = True) -> None:
    """Configure the root logger once, at application startup."""
    handler = logging.StreamHandler(sys.stdout)
    if json_output:
        handler.setFormatter(JsonFormatter())
    else:
        handler.setFormatter(
            logging.Formatter("%(asctime)s %(levelname)s %(name)s: %(message)s")
        )
    root = logging.getLogger()
    root.handlers.clear()
    root.addHandler(handler)
    root.setLevel(level)


configure_logging("INFO")
logger = logging.getLogger("orders_service.payments")


def charge(order_id: str, amount: str) -> None:
    logger.info("charging card", extra={"order_id": order_id, "amount": amount})
    try:
        raise ConnectionError("gateway timeout")        # stands in for a real call
    except ConnectionError:
        logger.exception("charge failed", extra={"order_id": order_id})


charge("A-1001", "64.49")
```

Output, one JSON object per line (the second line is wrapped here for reading, and the time will differ):

```text
{"time": "2026-03-01T10:15:02.114000+00:00", "level": "INFO", "logger": "orders_service.payments", "message": "charging card", "order_id": "A-1001", "amount": "64.49"}
{"time": "...", "level": "ERROR", "logger": "orders_service.payments", "message": "charge failed", "order_id": "A-1001", "exception": "Traceback (most recent call last):\n  ...\nConnectionError: gateway timeout"}
```

Writing to standard output lets the platform running the service (a container runtime, a process manager) collect and ship the logs, so the application does not manage log files at all. Searching for `order_id = A-1001` in a log tool then finds every event that belongs to that order, across services.

## Common Mistakes

- Using `print` in a service.
- Calling `logging.basicConfig` inside library code or at import time.
- Formatting messages with f-strings instead of passing arguments.
- Logging secrets, tokens, or personal data.
- Logging an exception and then raising it again at every layer, producing many duplicate entries.
- Using `logger.error(str(exc))` instead of `logger.exception`, losing the traceback.
- Leaving the level at the default `WARNING` and wondering why `INFO` messages never appear.
- Using the root logger directly (`logging.info(...)`) instead of a module logger.

## Summary

Use `logging` instead of `print` in anything that runs unattended. Create one logger per module with `getLogger(__name__)`, choose levels deliberately, pass arguments instead of preformatted strings, and use `logger.exception` inside `except` blocks to keep the traceback. Libraries only create loggers. Applications configure handlers and formatters once at startup, ideally with `dictConfig`, and emit structured JSON to standard output so logs can be searched by field.
