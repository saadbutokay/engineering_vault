# 5.2 Custom Exceptions

## Overview

Built-in exceptions describe general problems. Applications have their own kinds of failure: an order that does not exist, a payment that was declined, a rule that was violated. Custom exceptions give those failures names, so callers can handle them precisely and so the code explains itself.

## Defining a Custom Exception

Subclass `Exception` and, by convention, end the name with `Error`.

```python
class InsufficientFundsError(Exception):
    """Raised when an account balance is too low for a withdrawal."""


def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(f"balance {balance} is below requested {amount}")
    return balance - amount


try:
    withdraw(50, 80)
except InsufficientFundsError as exc:
    print(f"Declined: {exc}")
```

The class needs no body beyond a docstring. It inherits everything it needs from `Exception`. Never inherit from `BaseException`.

## Adding Information

Attach data the handler needs as attributes, and pass the message to `super().__init__` so `str(exc)` still works.

```python
class InsufficientFundsError(Exception):
    def __init__(self, balance, requested):
        super().__init__(f"balance {balance} is below requested {requested}")
        self.balance = balance
        self.requested = requested
        self.shortfall = requested - balance


try:
    raise InsufficientFundsError(50, 80)
except InsufficientFundsError as exc:
    print(exc.shortfall)     # 30
```

## Designing an Exception Hierarchy

For an application, define one base exception and derive specific ones from it.

```python
class AppError(Exception):
    """Base class for all errors raised deliberately by this application."""


class ValidationError(AppError):
    """Input data is invalid."""


class NotFoundError(AppError):
    """A requested resource does not exist."""


class ConflictError(AppError):
    """The request conflicts with the current state."""


class ExternalServiceError(AppError):
    """A dependency such as a payment provider failed."""
```

Benefits:

- Callers can catch one specific error (`NotFoundError`) or everything the application raises on purpose (`AppError`).
- Application errors are distinct from bugs. A `TypeError` is a defect to investigate, while a `NotFoundError` is an expected outcome to handle.
- A single place, such as a web framework error handler, can translate any `AppError` into a response.

Design guidelines:

- Keep the hierarchy shallow. Two or three levels are normally enough.
- Create a new class only when a caller will want to handle that case differently.
- Name classes after what went wrong, not where it happened.
- Put the base exceptions in one module such as `errors.py` that every other module can import.
- Do not wrap built-in exceptions needlessly. `ValueError` is perfectly good for a simple bad argument in a small function.

## ExceptionGroup and except*

Python 3.11 added `ExceptionGroup`, a container that holds several unrelated exceptions raised together. It is used when more than one thing can fail at once: concurrent tasks, batch validation, cleanup steps that each fail.

```python
group = ExceptionGroup(
    "several problems",
    [ValueError("bad quantity"), TypeError("bad price"), KeyError("sku")],
)
```

The `except*` syntax handles part of a group. Each `except*` clause receives a new group containing only the matching exceptions, and unmatched exceptions continue to propagate.

```python
try:
    raise group
except* ValueError as value_errors:
    print("value errors:", value_errors.exceptions)
except* (TypeError, KeyError) as others:
    print("others:", others.exceptions)
```

Rules to remember:

- The `except*` variable is always an `ExceptionGroup`, even when it matched only one exception. Use `.exceptions` to read the members.
- You cannot mix `except` and `except*` in the same `try` statement.
- The group's members must be `Exception` instances.
- Asynchronous task groups raise `ExceptionGroup` when several tasks fail.

## Adding Notes to Exceptions

Python 3.11 also added `add_note`, which attaches extra context to an existing exception without changing its type or message. The notes are printed after the message in the traceback.

```python
def parse_row(row_number, row):
    try:
        return int(row["quantity"])
    except (KeyError, ValueError) as exc:
        exc.add_note(f"while parsing row {row_number}: {row!r}")
        raise


try:
    parse_row(7, {"quantity": "x"})
except ValueError as exc:
    print(exc.__notes__)    # ["while parsing row 7: {'quantity': 'x'}"]
```

This is useful when an error occurs deep in a call chain and a higher layer knows the context, such as which row, file, or request was being processed.

## Basic Examples

```python
class NegativeNumberError(ValueError):
    """A number that must not be negative was negative."""


def square_root(x):
    if x < 0:
        raise NegativeNumberError(f"cannot take square root of {x}")
    return x ** 0.5


try:
    square_root(-4)
except ValueError as exc:                 # catches the subclass too
    print(type(exc).__name__, exc)
    # NegativeNumberError cannot take square root of -4
```

Inheriting from `ValueError` here means that existing code that handles `ValueError` still works with the new exception.

## Backend Industry Example

An application exception hierarchy that carries an HTTP status code and an error code, a single translation function for the web layer, and a batch validator that reports every bad row at once instead of stopping at the first.

```python
class AppError(Exception):
    """Base class for all deliberate application errors."""

    status_code = 500
    error_code = "app_error"

    def __init__(self, message: str, *, details: dict | None = None) -> None:
        super().__init__(message)
        self.message = message
        self.details = details or {}


class ValidationError(AppError):
    status_code = 400
    error_code = "validation_error"


class NotFoundError(AppError):
    status_code = 404
    error_code = "not_found"


class ConflictError(AppError):
    status_code = 409
    error_code = "conflict"


class ExternalServiceError(AppError):
    status_code = 502
    error_code = "external_service_error"


def to_response(exc: AppError) -> tuple[int, dict]:
    """Translate an application error into a status code and a JSON-ready body."""
    body = {"error": exc.error_code, "message": exc.message, "details": exc.details}
    return exc.status_code, body


def get_order(orders: dict[str, dict], order_id: str) -> dict:
    try:
        return orders[order_id]
    except KeyError:
        raise NotFoundError(f"order {order_id} does not exist") from None


try:
    get_order({}, "A-1")
except AppError as exc:
    print(to_response(exc))
# (404, {'error': 'not_found', 'message': 'order A-1 does not exist', 'details': {}})


def validate_row(row_number: int, row: dict) -> None:
    if not row.get("email"):
        raise ValidationError(
            f"row {row_number}: email is required", details={"row": row_number}
        )
    if int(row.get("quantity", 0)) <= 0:
        raise ValidationError(
            f"row {row_number}: quantity must be positive", details={"row": row_number}
        )


def validate_rows(rows: list[dict]) -> None:
    """Validate every row and raise one group containing all the problems."""
    errors = []
    for row_number, row in enumerate(rows, start=1):
        try:
            validate_row(row_number, row)
        except ValidationError as exc:
            errors.append(exc)
    if errors:
        raise ExceptionGroup("batch validation failed", errors)


rows = [
    {"email": "amina@example.com", "quantity": "2"},
    {"email": "", "quantity": "1"},
    {"email": "chen@example.com", "quantity": "0"},
]

try:
    validate_rows(rows)
except* ValidationError as problems:
    for problem in problems.exceptions:
        print(problem.message)
# row 2: email is required
# row 3: quantity must be positive
```

The status code lives on the exception class, so the web layer needs no chain of `if` statements: it reads `exc.status_code`. Collecting all problems in a group means a user uploading a file with many errors sees all of them in one response.

## Common Mistakes

- Defining a new exception class for every small case.
- Creating a deep hierarchy that nobody can remember.
- Subclassing `BaseException`, which prevents ordinary `except Exception` handlers from working.
- Forgetting to call `super().__init__(message)` so the message is lost.
- Putting sensitive data such as passwords or tokens in exception messages that end up in logs.
- Mixing `except` and `except*` in one `try` statement.
- Using custom exceptions for normal control flow in code that runs very frequently.

## Summary

Define custom exceptions by subclassing `Exception`, keep them in one module, and arrange them under a base application error. Add useful attributes such as status codes and details. Use `ExceptionGroup` and `except*` when several unrelated failures must be reported together, and `add_note` to attach context to an error as it travels up the call chain. Create new exception types only when callers need to handle them differently.
