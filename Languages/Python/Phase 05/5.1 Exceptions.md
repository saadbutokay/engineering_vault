# 5.1 Exceptions

## Overview

An exception is Python's way of signalling that something went wrong while a program runs: a missing file, bad input, a failed network call. When an exception is raised, normal execution stops and Python looks for code that handles it. If nothing does, the program ends with a traceback. Handling exceptions well separates robust software from fragile scripts.

## try and except

```python
try:
    number = int("abc")
except ValueError:
    print("That was not a whole number")
```

The code in `try` runs. If it raises a `ValueError`, execution jumps to the matching `except` block and the program continues afterwards. If no exception occurs, the `except` block is skipped.

Capture the exception object with `as` to read its message:

```python
try:
    number = int("abc")
except ValueError as exc:
    print(f"Conversion failed: {exc}")
```

Handle several types with separate blocks or with a tuple:

```python
try:
    value = data[key] / divisor
except KeyError:
    print("missing key")
except (ZeroDivisionError, TypeError) as exc:
    print(f"bad value: {exc}")
```

Python checks the `except` blocks from top to bottom and runs the first one that matches. Put specific exceptions before general ones.

## else and finally

```python
try:
    file = open("data.txt", encoding="utf-8")
except FileNotFoundError:
    print("no data file")
else:
    # runs only if the try block raised nothing
    print(file.read())
    file.close()
finally:
    # runs always: after success, after a handled error, and even after an unhandled one
    print("done")
```

- `else` holds code that should run only when `try` succeeded. It keeps the `try` block small so you do not accidentally catch exceptions raised by that code.
- `finally` holds cleanup that must happen regardless of what occurred. It runs even if the `try` block returns or an exception is not handled.

## The Built-in Exception Hierarchy

Exceptions are classes arranged in a tree. Catching a parent class catches all of its children.

```text
BaseException
  SystemExit
  KeyboardInterrupt
  GeneratorExit
  Exception
    ArithmeticError
      ZeroDivisionError
      OverflowError
    AssertionError
    AttributeError
    ImportError
      ModuleNotFoundError
    LookupError
      IndexError
      KeyError
    NameError
      UnboundLocalError
    OSError
      FileNotFoundError
      FileExistsError
      PermissionError
      IsADirectoryError
      TimeoutError
      ConnectionError
    RuntimeError
      NotImplementedError
      RecursionError
    StopIteration
    TypeError
    ValueError
      UnicodeError
```

Points to remember:

- Almost everything you handle inherits from `Exception`.
- `KeyboardInterrupt` (Ctrl+C) and `SystemExit` inherit from `BaseException` so that `except Exception` does not trap them. Never catch `BaseException` or write a bare `except:` unless you re-raise.
- `LookupError` covers both `KeyError` and `IndexError`. `OSError` covers most file and network failures. `json.JSONDecodeError` is a subclass of `ValueError`.

## raise

Use `raise` to signal an error yourself.

```python
def withdraw(balance, amount):
    if amount <= 0:
        raise ValueError("amount must be positive")
    if amount > balance:
        raise ValueError(f"insufficient funds: balance {balance}, requested {amount}")
    return balance - amount
```

Choose the built-in type that matches the problem: `ValueError` for a bad value, `TypeError` for a wrong type, `KeyError` or `LookupError` for something missing, `NotImplementedError` for an unfinished method.

A bare `raise` inside an `except` block re-raises the current exception with its original traceback. Use it when you want to do something, such as logging, and then let the error continue.

```python
try:
    process(order)
except Exception:
    logger.error("order failed")
    raise
```

## Exception Chaining

When you catch one exception and raise another, use `from` to link them. The traceback then shows both, with the explanation "The above exception was the direct cause of the following exception".

```python
def load_age(raw):
    try:
        return int(raw)
    except ValueError as exc:
        raise ValueError(f"age must be a whole number, got {raw!r}") from exc
```

If you raise inside an `except` block without `from`, Python still records the earlier exception as context and prints "During handling of the above exception, another exception occurred". Use `from exc` to state that the link is deliberate. Use `from None` to hide the original when it is only noise to the caller.

## EAFP versus LBYL

- LBYL (look before you leap): check conditions first.
- EAFP (easier to ask forgiveness than permission): try the operation and handle the failure.

```python
import os

# LBYL: the file can disappear between the check and the open
if os.path.exists("settings.toml"):
    with open("settings.toml", encoding="utf-8") as f:
        text = f.read()

# EAFP: one step, no gap between check and use
try:
    with open("settings.toml", encoding="utf-8") as f:
        text = f.read()
except FileNotFoundError:
    text = ""
```

Python favours EAFP. It avoids race conditions between the check and the action, and it handles every failure cause (missing, permission denied, is a directory) in one place. LBYL is still the right choice for cheap, simple checks such as `if key in mapping`, or when an exception would be confusing for ordinary flow.

## Writing Good Exception Handling

- Catch the most specific exception you can handle meaningfully.
- Keep the `try` block as small as possible.
- Never swallow errors silently with `except: pass`.
- Do not catch an exception unless you can recover, add information, translate it, or log it at a boundary.
- Clean up resources with `finally` or, better, with a `with` statement.
- Write error messages that include the offending value and what was expected.

## Basic Examples

```python
def safe_divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return None

print(safe_divide(10, 2))    # 5.0
print(safe_divide(10, 0))    # None

def read_number():
    while True:
        text = input("Number: ")
        try:
            return float(text)
        except ValueError:
            print("Please enter a valid number.")

scores = {"amina": 90}
try:
    print(scores["bilal"])
except KeyError as exc:
    print(f"no score for {exc}")
```

## Backend Industry Example

A request handler that validates input, translates low-level errors into meaningful ones, and maps each kind of failure to an HTTP-style status code. Only the outermost boundary uses a broad `except Exception`, and it logs the full traceback.

```python
import logging
import time

logger = logging.getLogger(__name__)


def parse_quantity(raw: object) -> int:
    """Convert a client-supplied quantity into a positive integer."""
    try:
        quantity = int(raw)
    except (TypeError, ValueError) as exc:
        raise ValueError(f"quantity must be a whole number, got {raw!r}") from exc
    if quantity <= 0:
        raise ValueError(f"quantity must be positive, got {quantity}")
    return quantity


def reserve_stock(inventory: dict[str, int], sku: str, quantity: int) -> None:
    """Remove stock for an order or raise a descriptive error."""
    try:
        available = inventory[sku]
    except KeyError:
        raise LookupError(f"unknown product {sku!r}") from None
    if quantity > available:
        raise ValueError(f"only {available} units of {sku} are in stock")
    inventory[sku] = available - quantity


def handle_order(payload: dict, inventory: dict[str, int]) -> tuple[int, dict]:
    """Process an order payload and return (http_status, response_body)."""
    started = time.perf_counter()
    try:
        sku = payload["sku"]
        quantity = parse_quantity(payload["quantity"])
        reserve_stock(inventory, sku, quantity)
    except KeyError as exc:
        status, body = 400, {"error": f"missing field {exc}"}
    except ValueError as exc:
        status, body = 400, {"error": str(exc)}
    except LookupError as exc:
        status, body = 404, {"error": str(exc)}
    except Exception:
        logger.exception("unexpected failure while handling order")
        status, body = 500, {"error": "internal server error"}
    else:
        status, body = 201, {"sku": sku, "reserved": quantity}
    finally:
        elapsed_ms = (time.perf_counter() - started) * 1000
        logger.info("order handled in %.2f ms", elapsed_ms)
    return status, body


stock = {"pen": 10}
print(handle_order({"sku": "pen", "quantity": "3"}, stock))    # (201, ...)
print(handle_order({"sku": "pen", "quantity": "abc"}, stock))  # (400, ...)
print(handle_order({"sku": "pen"}, stock))                     # (400, ...)
print(handle_order({"sku": "ink", "quantity": 1}, stock))      # (404, ...)
print(handle_order({"sku": "pen", "quantity": 50}, stock))     # (400, ...)
```

Several habits are visible here. `KeyError` is caught before the broader `LookupError`, because a `KeyError` is a kind of `LookupError`. With the order reversed, the `KeyError` block could never run. `raise ... from exc` keeps the cause visible and `from None` removes noise. `else` holds the success path and `finally` always records the timing. The client receives a safe message for unexpected errors while the log receives the full traceback.

## Common Mistakes

- Writing a bare `except:` or `except Exception: pass`, which hides bugs and even catches Ctrl+C when bare.
- Putting a large block of code inside `try` and catching exceptions that came from somewhere unexpected.
- Catching an exception just to print it and then continuing as if nothing happened.
- Placing a general `except` before a specific one, so the specific block can never run.
- Using exceptions with messages like "error" and no values.
- Returning `None` or an error code from functions instead of raising, so callers forget to check.
- Raising a new exception in an `except` block without `from`, losing the clear link to the cause.

## Summary

Use `try`, `except`, `else`, and `finally` to handle failures, with specific exception types and small `try` blocks. Know the built-in hierarchy so you catch the right level, and raise exceptions yourself with informative messages. Chain errors with `raise ... from`, prefer EAFP for operations that can fail, and handle unexpected exceptions only at program boundaries, where they are logged in full.
