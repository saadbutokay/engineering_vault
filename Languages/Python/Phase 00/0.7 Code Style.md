# 0.7 Code Style

## Overview

Code is read far more often than it is written. A shared style makes code predictable, which makes it easier to review, debug, and maintain. Python has official style documents, and teams enforce them with tools so nobody argues about formatting.

## PEP 8

PEP 8 is the official style guide for Python code. Its key rules:

- Indent with 4 spaces. Never mix tabs and spaces.
- Use two blank lines between top-level functions and classes, and one blank line between methods inside a class.
- Put imports at the top of the file, one per line, in three groups separated by a blank line: standard library, third-party packages, then your own modules.
- Put spaces around operators and after commas: `x = a + b`, `f(a, b)`. Do not put spaces just inside brackets or before a call's parentheses.
- Compare to `None` with `is` or `is not`, never `==`.
- Avoid single-letter names `l`, `O`, and `I`, which look like digits.

## PEP 20: The Zen of Python

PEP 20 is a short set of guiding principles. Run this to read it in full:

```python
import this
```

Principles worth remembering:

- Explicit is better than implicit.
- Simple is better than complex.
- Readability counts.
- Errors should never pass silently.

These are not rules to enforce mechanically. They are a way of choosing between two working solutions: prefer the one the next reader will understand faster.

## Naming Conventions

| Kind | Convention | Example |
| --- | --- | --- |
| Variables and functions | `snake_case` | `order_total`, `calculate_tax` |
| Classes | `PascalCase` | `OrderService`, `PaymentError` |
| Constants | `UPPER_SNAKE_CASE` | `MAX_RETRIES` |
| Modules and packages | short lowercase names | `orders`, `billing` |
| Internal use only | leading underscore | `_cache`, `_parse_row` |

Choose names that describe meaning, not type or abbreviation. `customer_email` is better than `ce` or `string1`. Functions are usually verbs (`send_invoice`), and booleans read well as questions (`is_active`, `has_permission`).

## Line Length

PEP 8 recommends 79 characters, and 72 for comments and docstrings. Many modern teams use 88 (the default of the Black and Ruff formatters) or 100. The exact number matters less than agreeing on one and letting a formatter enforce it. Break long lines inside brackets rather than with backslashes.

## Docstrings

A docstring is a string placed as the first statement of a module, class, or function. Tools and editors display it as documentation. Two common styles are Google style and NumPy style.

Google style:

```python
def add(a, b):
    """Add two numbers.

    Args:
        a: The first number.
        b: The second number.

    Returns:
        The sum of a and b.
    """
    return a + b
```

NumPy style:

```python
def add(a, b):
    """
    Add two numbers.

    Parameters
    ----------
    a : int
        The first number.
    b : int
        The second number.

    Returns
    -------
    int
        The sum of a and b.
    """
    return a + b
```

Backend teams most often choose Google style because it is compact. NumPy style is common in scientific and data libraries. Pick one per project and stay consistent. A good docstring starts with a one-line summary in the imperative mood, such as "Return the total" rather than "Returns the total".

## Basic Examples

Poor style:

```python
def f(x,y):
  l=[]
  for i in x:
    if i>y: l.append(i)
  return l
```

Same logic in the recommended style:

```python
def filter_above_threshold(values, threshold):
    """Return the values that are greater than the threshold."""
    result = []
    for value in values:
        if value > threshold:
            result.append(value)
    return result
```

The behaviour is identical. The second version tells the reader what it does, uses clear names, and follows standard spacing and indentation.

## Backend Industry Example

A pricing function written the way it would appear in a real service: grouped imports, constants, type hints, a Google-style docstring, validation with specific errors, and `Decimal` for money.

```python
"""Pricing utilities for the orders service."""

import logging
from decimal import Decimal

MAX_DISCOUNT_RATE = Decimal("0.30")

logger = logging.getLogger(__name__)


def apply_discount(subtotal: Decimal, discount_rate: Decimal) -> Decimal:
    """Apply a percentage discount to an order subtotal.

    Args:
        subtotal: The order total before the discount, in the account currency.
        discount_rate: The discount as a fraction, for example Decimal("0.10")
            for ten percent.

    Returns:
        The discounted total, rounded to two decimal places.

    Raises:
        ValueError: If the subtotal is negative or the discount rate is outside
            the allowed range.
    """
    if subtotal < 0:
        raise ValueError("subtotal must not be negative")
    if not Decimal("0") <= discount_rate <= MAX_DISCOUNT_RATE:
        raise ValueError(f"discount_rate must be between 0 and {MAX_DISCOUNT_RATE}")

    discounted = subtotal * (Decimal("1") - discount_rate)
    logger.debug("Applied discount rate %s to subtotal %s", discount_rate, subtotal)
    return discounted.quantize(Decimal("0.01"))
```

Details to notice: the module docstring explains purpose, the constant has a meaningful name instead of a magic number, the logger is created once per module, and log arguments are passed separately instead of pre-formatted so formatting only happens if the message is actually emitted.

## Common Mistakes

- Inconsistent naming within one codebase, such as mixing `camelCase` and `snake_case`.
- Single-letter or abbreviated names outside very short loops.
- Comments that repeat the code (`# add one` above `x += 1`) instead of explaining why.
- Docstrings that describe the implementation instead of the behaviour.
- Formatting by hand and arguing about it in code review instead of using a formatter.

## Summary

Follow PEP 8 for layout and naming, use the Zen of Python as a tiebreaker for design choices, choose one docstring style per project, and agree on a line length. Automate enforcement so style never consumes review time.
