# 0.6 Project Layout and Configuration

## Overview

How you arrange files decides how easy a project is to test, package, and hand over to others. This module covers the standard `src` layout, the purpose of `pyproject.toml`, what belongs in `.gitignore`, and how `.env` files keep secrets out of source code.

## The src Layout

```text
orders-service/
  pyproject.toml
  README.md
  .gitignore
  .env.example
  src/
    orders_service/
      __init__.py
      __main__.py
      config.py
  tests/
    test_config.py
```

| Item | Purpose |
| --- | --- |
| `src/orders_service/` | The importable package containing the application code |
| `tests/` | Tests, kept outside the package so they are not shipped |
| `pyproject.toml` | Project metadata, dependencies, and tool configuration |
| `README.md` | What the project is and how to run it |
| `.gitignore` | Files Git must never track |
| `.env.example` | Template listing required environment variables, without real values |

Why a `src` folder? Without it, Python can import your package straight from the current directory, so tests may pass on your machine even though the installed package is broken. With `src`, the package is only importable after installation, so tests exercise what users actually get. Install your project in editable mode during development:

```bash
python -m pip install -e .
```

Editable mode links the installed package to your source files, so edits take effect immediately.

## pyproject.toml Basics

`pyproject.toml` is the single standard configuration file for a Python project. It has tables for metadata, the build system, and tools.

```toml
[project]
name = "orders-service"
version = "0.1.0"
description = "Order processing service"
requires-python = ">=3.12"
dependencies = [
    "requests>=2.31",
]

[build-system]
requires = ["setuptools>=68"]
build-backend = "setuptools.build_meta"

[tool.setuptools.packages.find]
where = ["src"]
```

- `[project]` describes the project and its runtime dependencies.
- `[build-system]` tells installers how to build the project.
- `[tool.xxx]` tables hold configuration for tools such as ruff, mypy, and pytest.

## .gitignore

A `.gitignore` file lists patterns Git should ignore.

```text
# Virtual environments
.venv/
venv/

# Python bytecode and caches
__pycache__/
*.py[cod]
.pytest_cache/
.mypy_cache/
.ruff_cache/

# Build artifacts
build/
dist/
*.egg-info/

# Secrets and local configuration
.env
.env.*
!.env.example

# Editor and operating system files
.idea/
.DS_Store
```

The line starting with `!` re-includes `.env.example` even though `.env.*` would otherwise exclude it.

## .env Files and Secrets

A `.env` file holds configuration that differs between machines and must not be public: database URLs, API keys, signing secrets.

```text
DATABASE_URL=postgresql://app:change-me@localhost:5432/orders
SECRET_KEY=replace-with-a-long-random-value
DEBUG=true
```

Why secrets never go into code:

- Git history is permanent. A secret committed once remains in history even after the file is edited.
- Anyone with repository access, including contractors, bots, and future teammates, can read it.
- Automated scanners search public repositories for leaked keys within minutes.
- Different environments (development, staging, production) need different values. Code should be identical everywhere; only configuration changes.

The convention: keep the real `.env` out of Git and commit `.env.example` with placeholder values, so new developers know which variables to set. If a secret is ever committed, rotate it immediately. Deleting it from the latest commit is not enough.

## Basic Examples

Reading an environment variable:

```python
import os

database_url = os.environ.get("DATABASE_URL")
print(database_url)
```

`os.environ.get` returns `None` when the variable is missing instead of raising an error.

Loading a `.env` file during development with the `python-dotenv` package:

```python
from dotenv import load_dotenv
import os

load_dotenv()
print(os.environ["SECRET_KEY"])
```

## Backend Industry Example

A single configuration module reads everything the application needs, validates it once at startup, and exposes it as an immutable object. Missing required values stop the process immediately with a clear message, instead of failing later in the middle of a request.

```python
# src/orders_service/config.py
import os
from dataclasses import dataclass


@dataclass(frozen=True)
class Settings:
    database_url: str
    secret_key: str
    debug: bool = False


def _require(name: str) -> str:
    value = os.environ.get(name)
    if not value:
        raise RuntimeError(f"Missing required environment variable: {name}")
    return value


def load_settings() -> Settings:
    """Build application settings from environment variables."""
    return Settings(
        database_url=_require("DATABASE_URL"),
        secret_key=_require("SECRET_KEY"),
        debug=os.environ.get("DEBUG", "false").lower() == "true",
    )
```

In production the environment variables come from the deployment platform's secret store, not from a file on disk. The code is the same in every environment. The `@dataclass` syntax used here is a compact way to define a class that only holds values.

## Common Mistakes

- Committing `.env` before adding it to `.gitignore`.
- Placing tests inside the package, which ships them to users.
- Hard-coding database passwords or API keys "just for now".
- Reading environment variables all over the codebase instead of in one configuration module.
- Forgetting `__init__.py` or the editable install and then fighting import errors.

## Summary

Use the `src` layout with a separate `tests` folder, describe the project in `pyproject.toml`, and keep `.gitignore` complete from the first commit. Keep secrets in `.env` locally and in a secret store in production, commit only `.env.example`, and load settings in one validated place at startup.
