# 0.8 Git Essentials

## Overview

Git is a version control system. It records snapshots of your project over time so you can see what changed, undo mistakes, work on features in isolation, and collaborate with other developers. GitHub is a hosting service for Git repositories. Git is the tool and GitHub is one place to store the repository.

## First-Time Setup

Tell Git who you are. This information is attached to every commit.

```bash
git config --global user.name "Amina Rahman"
git config --global user.email "amina@example.com"
git config --global init.defaultBranch main
```

## The Core Workflow

Git has three areas: the working directory (your files), the staging area (changes selected for the next commit), and the repository (saved history).

```bash
git init                       # start tracking the current folder
git status                     # see what changed and what is staged
git add src/app.py             # stage one file
git add .                      # stage everything in the current folder
git commit -m "Add order total calculation"
git log --oneline              # compact history
git diff                       # changes not yet staged
git diff --staged              # changes staged for the next commit
```

Undoing:

```bash
git restore src/app.py             # discard unstaged changes in a file
git restore --staged src/app.py    # unstage a file but keep the changes
```

A commit is a saved snapshot with a message. Each commit should be one logical change with a message that explains it.

## Branches and Merging

A branch is an independent line of development. The default branch is usually `main`.

```bash
git branch                         # list branches
git switch -c feature/discounts    # create and move to a new branch
git switch main                    # return to main
git merge feature/discounts        # bring the branch's commits into main
git branch -d feature/discounts    # delete the merged branch
```

When two branches change the same lines, Git reports a merge conflict and marks the file:

```text
<<<<<<< HEAD
discount_rate = 0.10
=======
discount_rate = 0.15
>>>>>>> feature/discounts
```

Edit the file to keep the correct result, remove the markers, then stage and commit:

```bash
git add src/pricing.py
git commit
```

## Remotes and GitHub

A remote is a copy of the repository hosted elsewhere.

```bash
git remote add origin https://github.com/your-user/orders-service.git
git push -u origin main        # first push; sets the upstream branch
git push                       # later pushes
git pull                       # fetch and merge new commits from the remote
git clone https://github.com/your-user/orders-service.git
```

## What to Commit and What to Ignore

Commit:

- Source code and tests
- `pyproject.toml`, lock files, and `requirements.txt`
- `README.md` and documentation
- `.env.example` and tool configuration

Ignore (put in `.gitignore`):

- Virtual environments such as `.venv/`
- Secrets such as `.env`
- Generated files: `__pycache__/`, `.pytest_cache/`, `dist/`, `build/`
- Large datasets and local logs

A `.gitignore` only affects files that are not already tracked. If a file was committed by mistake, remove it from tracking with `git rm --cached filename`, then commit.

## Basic Examples

A complete first session:

```bash
mkdir hello-git
cd hello-git
git init
echo "print('hello')" > hello.py
git status
git add hello.py
git commit -m "Add hello script"
git log --oneline
```

## Backend Industry Example

Teams work on short-lived feature branches and merge through pull requests, so `main` always stays deployable.

```bash
git switch main
git pull
git switch -c feature/order-discount-validation

# edit code and tests, then check what you are about to commit
git status
git diff

git add src/orders_service/pricing.py tests/test_pricing.py
git commit -m "Validate discount rate range in apply_discount"

git push -u origin feature/order-discount-validation
```

Then open a pull request on GitHub, have it reviewed, let automated checks run, and merge. Delete the branch afterwards.

Habits that professional teams follow:

- Stage specific files instead of using `git add .` blindly, and review `git diff --staged` before each commit.
- Write commit messages in the imperative mood with a short summary line, for example "Fix rounding error in invoice totals".
- Keep commits small and focused so they can be reviewed and reverted individually.
- Never commit directly to `main` on a shared project.
- If a secret is committed, treat it as compromised and rotate it. Removing it in a later commit does not remove it from history.

## Common Mistakes

- Committing `.venv`, `.env`, or cache folders because `.gitignore` was created too late.
- Using vague messages such as "fix" or "update".
- Making one huge commit containing unrelated changes.
- Working directly on `main`.
- Using `git add .` without checking `git status` first.
- Panicking in a merge conflict instead of reading the markers carefully.

## Summary

Learn the cycle of status, add, commit, and log until it is automatic. Use branches for every feature, merge through pull requests, and push to a remote such as GitHub. Commit source, tests, and configuration; ignore environments, secrets, and generated files. Small commits with clear messages make a project's history useful.
