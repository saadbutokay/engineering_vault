# 0.5 Virtual Environments and Packages

## Overview

A virtual environment is an isolated folder containing its own Python interpreter and its own set of installed packages. It lets every project have the dependencies it needs without interfering with other projects or with the operating system's Python.

## Why Isolation Matters

- Project A needs version 1 of a library and project B needs version 2. A single global installation cannot satisfy both.
- Installing packages globally can break system tools, especially on Linux and macOS.
- Reproducibility: a teammate or a server should be able to recreate exactly the same set of packages.
- Cleanliness: deleting the environment folder removes everything the project installed.

## Creating and Activating with venv

`venv` is part of the standard library.

```bash
python3 -m venv .venv          # macOS and Linux
python -m venv .venv           # Windows
```

This creates a `.venv` folder in the project. Activate it so the shell uses its interpreter.

| Shell | Activation command |
| --- | --- |
| PowerShell (Windows) | `.venv\Scripts\Activate.ps1` |
| Command Prompt (Windows) | `.venv\Scripts\activate.bat` |
| zsh or bash (macOS and Linux) | `source .venv/bin/activate` |

When active, the prompt starts with `(.venv)`. Leave the environment with:

```bash
deactivate
```

If PowerShell refuses to run the activation script, allow locally created scripts for your user once:

```powershell
Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned
```

## Installing Packages with pip

```bash
python -m pip install requests                 # latest version
python -m pip install "requests==2.32.3"       # exact version
python -m pip install "requests>=2.31,<3"      # version range
python -m pip install -r requirements.txt      # everything listed in a file
python -m pip list                             # installed packages
python -m pip show requests                    # details about one package
python -m pip uninstall requests
```

## Recording Dependencies

```bash
python -m pip freeze > requirements.txt
```

`pip freeze` lists every installed package with its exact version, including packages that were installed only because another package needed them (transitive dependencies). Anyone can recreate the environment later:

```bash
python -m pip install -r requirements.txt
```

## Using uv

`uv` provides the same workflow with much faster resolution and installation.

```bash
uv venv                                    # create .venv
uv pip install requests                    # install into the environment
uv pip install -r requirements.txt
uv pip freeze                              # list installed packages
uv pip compile requirements.in -o requirements.txt    # resolve and lock versions
uv pip sync requirements.txt               # make the environment match the file exactly
```

## Basic Examples

Check from Python whether you are inside a virtual environment:

```python
import sys

in_venv = sys.prefix != sys.base_prefix
print("Inside virtual environment:", in_venv)
print("Interpreter:", sys.executable)
```

Use an installed third-party package:

```python
import requests

response = requests.get("https://example.com")
print(response.status_code)
```

If this fails with `ModuleNotFoundError` the package was installed into a different environment than the one running the script.

## Backend Industry Example

Professional projects separate what the project asks for from what was resolved.

`requirements.in` lists only direct dependencies, loosely constrained:

```text
requests>=2.31
sqlalchemy>=2.0
```

Compile it into a fully pinned lock file, including hashes that protect against tampered packages:

```bash
uv pip compile requirements.in -o requirements.txt --generate-hashes
```

`requirements.txt` now contains every package pinned to an exact version. Commit both files. The same `requirements.txt` is installed in development, CI, and production, so all three behave identically.

The container build uses the lock file and copies it before the source code, so Docker can cache the dependency layer:

```dockerfile
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ ./src/
ENV PYTHONPATH=/app/src

CMD ["python", "-m", "orders_service", "healthcheck"]
```

Inside a container, a virtual environment is optional because the container itself is already an isolated environment. Many teams still use one for consistency.

## Common Mistakes

- Installing packages while the environment is not activated, so they go to the global interpreter.
- Committing the `.venv` folder to Git. It is large, machine-specific, and recreatable.
- Using `pip freeze` output as the only dependency record, which mixes direct and transitive dependencies and makes upgrades hard to reason about.
- Moving or renaming a project folder and expecting the environment to keep working. Recreate it instead.
- Leaving dependencies unpinned in production and getting different behaviour after a rebuild.

## Summary

Create one virtual environment per project with `python -m venv .venv` or `uv venv`, activate it, and install packages into it with pip or uv. Record dependencies in `requirements.txt`. In production-grade projects, keep a loose `requirements.in`, compile it to a pinned lock file, and install that file everywhere.
