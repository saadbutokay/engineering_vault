# 4.2 Packages

## Overview

A package is a folder of modules. Packages let you organize a project into a hierarchy, with names like `orders_service.models.order`, and avoid name clashes between unrelated modules. This module covers how packages are structured, how to import within them, and how to control what a package exposes.

## Package Structure

A folder becomes a regular package when it contains a file named `__init__.py`. That file can be empty, or it can contain code that runs when the package is first imported.

```text
orders_service/
    __init__.py
    config.py
    pricing.py
    models/
        __init__.py
        order.py
        customer.py
    services/
        __init__.py
        checkout.py
```

Here `orders_service` is a package, `models` and `services` are subpackages, and `order.py` is a module inside a subpackage. Importing uses dots to follow the folder structure:

```python
import orders_service.pricing
from orders_service.models.order import Order
from orders_service import config
```

Importing a package runs its `__init__.py`. Importing `orders_service.models.order` runs `orders_service/__init__.py`, then `models/__init__.py`, then `order.py`, in that order.

## Absolute and Relative Imports

An absolute import spells out the full path from the top-level package:

```python
# inside orders_service/services/checkout.py
from orders_service.models.order import Order
from orders_service.pricing import apply_discount
```

A relative import describes the location relative to the current module, using leading dots:

```python
# inside orders_service/services/checkout.py
from ..models.order import Order       # up one level, then into models
from ..pricing import apply_discount   # up one level
from . import helpers                  # a sibling module in services
from .helpers import format_money      # a name from that sibling
```

| Dots | Meaning |
| --- | --- |
| `.` | the current package |
| `..` | the parent package |
| `...` | two levels up |

Guidance:

- Absolute imports are clearer and are the default recommendation, because the full path is visible and the line stays valid if the module moves within its package.
- Relative imports are acceptable inside a package for closely related modules, especially in `__init__.py`.
- Relative imports only work inside a package. Running a file directly with `python checkout.py` fails with `ImportError: attempted relative import with no known parent package`. Run it as a module from the project root instead, with `python -m orders_service.services.checkout`.

## Namespace Packages

A folder without `__init__.py` can still be imported. Python treats it as a namespace package, and one such package can be spread across several directories, which is how some large libraries are split into separately installed parts. For your own application code, include `__init__.py` in every package folder. It makes the structure explicit and avoids accidental imports of folders that were never meant to be packages.

## `__init__.py` and the Public API

`__init__.py` is the place to decide what users of the package see. It can re-export the important names so that callers do not need to know the internal file layout.

```python
# orders_service/__init__.py
"""Orders service: pricing, models, and checkout."""

from .models.order import Order
from .pricing import apply_discount

__version__ = "0.1.0"
__all__ = ["Order", "apply_discount", "__version__"]
```

Users can now write:

```python
from orders_service import Order, apply_discount
```

instead of importing from the full internal paths.

`__all__` is a list of strings naming the public names of a module or package. It does two things: it controls what `from package import *` imports, and it documents which names are intended to be used from outside. Tools such as linters and documentation generators also read it.

Keep `__init__.py` light. A heavy `__init__.py` that imports many modules makes importing the package slow, makes circular imports more likely, and hides where things are defined.

## Running Modules Inside a Package

Use `-m` with the dotted module path from the project root:

```bash
python -m orders_service.pricing
python -m orders_service            # runs orders_service/__main__.py
```

This keeps relative imports working and puts the project root on the import path.

## Basic Examples

A small package called `geometry`:

```text
geometry/
    __init__.py
    circles.py
    rectangles.py
```

```python
# geometry/circles.py
import math

def area(radius):
    return math.pi * radius ** 2
```

```python
# geometry/rectangles.py
def area(width, height):
    return width * height
```

```python
# geometry/__init__.py
from . import circles, rectangles
```

```python
# main.py, in the folder that contains geometry/
import geometry
from geometry import circles
from geometry.rectangles import area as rectangle_area

print(round(geometry.circles.area(1), 2))    # 3.14
print(rectangle_area(3, 4))                  # 12
```

## Backend Industry Example

The skeleton of a service package. Each file has one job, the models know nothing about services, and the package root exposes a small public API.

```python
# src/orders_service/pricing.py
"""Pricing rules."""

from decimal import ROUND_HALF_UP, Decimal

CENTS = Decimal("0.01")


def apply_discount(subtotal: Decimal, discount_rate: Decimal) -> Decimal:
    """Return the subtotal after the discount, rounded to cents."""
    discounted = subtotal * (Decimal("1") - discount_rate)
    return discounted.quantize(CENTS, rounding=ROUND_HALF_UP)
```

```python
# src/orders_service/models/order.py
"""The Order model."""

from dataclasses import dataclass
from decimal import Decimal

from ..pricing import apply_discount


@dataclass
class Order:
    order_id: str
    subtotal: Decimal
    discount_rate: Decimal = Decimal("0")

    def total(self) -> Decimal:
        """Return the amount the customer pays."""
        return apply_discount(self.subtotal, self.discount_rate)
```

```python
# src/orders_service/models/__init__.py
from .order import Order

__all__ = ["Order"]
```

```python
# src/orders_service/services/__init__.py
```

```python
# src/orders_service/services/checkout.py
"""Checkout use case."""

from orders_service.models import Order


def checkout_summary(order: Order) -> str:
    """Return a one-line description of an order."""
    return f"Order {order.order_id}: total {order.total()}"
```

```python
# src/orders_service/__init__.py
"""Orders service: pricing, models, and checkout."""

from .models import Order
from .pricing import apply_discount

__version__ = "0.1.0"
__all__ = ["Order", "apply_discount", "__version__"]
```

Using the package from outside, after an editable install of the project:

```python
from decimal import Decimal

from orders_service import Order
from orders_service.services.checkout import checkout_summary

order = Order("A-1001", Decimal("200.00"), Decimal("0.10"))
print(checkout_summary(order))    # Order A-1001: total 180.00
```

The package root re-exports `Order` and `apply_discount`, so most callers never depend on the internal structure. Anything not listed in `__all__`, such as `CENTS`, is understood to be internal.

## Common Mistakes

- Forgetting `__init__.py` in a package folder and wondering why some tools cannot find it.
- Running a file inside a package directly and getting the relative import error. Use `python -m`.
- Putting heavy logic or many imports in `__init__.py`.
- Creating a module with the same name as its package, or the same name as a standard library module.
- Using `from package import *` in application code.
- Deep nesting with only one module per folder. Keep the structure as flat as it can be while staying clear.
- Mixing absolute and relative imports without any consistent rule.

## Summary

A package is a folder with an `__init__.py`, imported with dotted names. Prefer absolute imports, use relative imports sparingly within a package, and run package modules with `python -m`. Use `__init__.py` and `__all__` to define the public API of a package and keep both light. Include `__init__.py` in your own packages rather than relying on namespace packages.
