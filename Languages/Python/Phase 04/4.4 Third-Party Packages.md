# 4.4 Third-Party Packages

## Overview

Much of real-world Python work is assembling well-tested libraries written by others: HTTP clients, database drivers, validation, web frameworks, testing tools. These libraries are shared through the Python Package Index (PyPI) and installed with `pip` or `uv`. Every dependency you add is also code you must trust and maintain, so choosing and managing them carefully is a professional skill.

## Finding Packages on PyPI

PyPI is the public repository at pypi.org. Each package has a project page showing:

- The latest version and its release history
- A description, usually the project's README
- Links to the source repository, documentation, and issue tracker
- The license and supported Python versions
- The maintainers

Search on pypi.org, read the project page, and follow its links to the repository. The `pip search` command no longer works because PyPI disabled it, so use the website or the project's own documentation.

Before adding any package, check whether the standard library already does the job. `pathlib`, `json`, `csv`, `sqlite3`, `argparse`, `logging`, `urllib`, and `datetime` cover a surprising amount.

## Installing Packages

Always install into an active virtual environment.

```bash
python -m pip install requests               # latest version
python -m pip install "requests==2.32.3"     # an exact version
python -m pip install "requests>=2.31,<3"    # a range
python -m pip install -U requests            # upgrade to the latest
python -m pip install "httpx[http2]"         # a package plus one of its optional extras
python -m pip uninstall requests
python -m pip list                           # everything installed
python -m pip list --outdated                # what has newer versions
python -m pip show requests                  # version, location, dependencies
```

With `uv`:

```bash
uv pip install requests
uv add requests            # in a uv project: installs and records it in pyproject.toml
uv remove requests
```

## Pinning Versions

A version number has the form `major.minor.patch`, for example `2.32.3`. Under semantic versioning, a major version change may break compatibility, a minor one adds features, and a patch one fixes bugs. Not every project follows this strictly, so read changelogs.

Version specifiers:

| Specifier | Meaning |
| --- | --- |
| `requests==2.32.3` | exactly this version |
| `requests>=2.31` | this version or newer |
| `requests>=2.31,<3` | newer than 2.31 but below 3 |
| `requests~=2.32` | compatible release: `>=2.32` and `<3.0` |
| `requests~=2.32.1` | compatible release: `>=2.32.1` and `<2.33` |
| `requests!=2.32.0` | any version except this one |

Libraries you publish should declare wide, compatible ranges so they work with other libraries. Applications you deploy should pin exact versions through a lock file, so the same versions are installed in development, testing, and production.

## Lock Files

A lock file records the exact version of every package, including transitive dependencies (the dependencies of your dependencies), usually with file hashes.

Common approaches:

```bash
# requirements.txt as a lock file, generated from a loose requirements.in
uv pip compile requirements.in -o requirements.txt --generate-hashes
uv pip sync requirements.txt

# uv project workflow: dependencies in pyproject.toml, locked in uv.lock
uv add requests
uv lock                     # resolve and write uv.lock
uv sync --locked            # install exactly what uv.lock says, fail if it is out of date
uv run pytest               # run a command inside the project's environment
```

Other tools such as Poetry (`poetry.lock`) and pip-tools provide the same idea. Commit the lock file to Git. Update it deliberately, review what changed, and run the tests.

## Reading Package Documentation

When you adopt a package, read in this order:

1. The README on PyPI or the repository, for what it does and a short example.
2. The quickstart or tutorial on the documentation site (often on Read the Docs or the project's own site).
3. The API reference, for exact function signatures and parameters.
4. The changelog or release notes, to understand what changed between versions and whether upgrades are risky.
5. The source code, when the documentation is not enough. Python makes this easy.

Tools available inside Python:

```python
import requests

help(requests.get)           # signature and docstring
print(dir(requests))         # names the package provides
print(requests.__file__)     # where the code lives on disk
print(requests.__version__)
```

```bash
python -m pydoc requests.get
```

## Evaluating Package Quality

Before depending on a package, ask:

| Question | What to look for |
| --- | --- |
| Is it maintained? | Recent releases and commits, maintainers who answer issues and fix bugs |
| Is it widely used? | Download counts, other well-known projects depending on it. Popularity helps but does not prove quality |
| Is it documented? | A clear quickstart and an API reference |
| Is it tested? | A test suite and continuous integration visible in the repository |
| Is the license acceptable? | Compatible with your project and employer |
| How big is its dependency tree? | Many transitive dependencies mean more to update and more risk |
| Does it support your Python version? | Check supported versions and that it works with current releases |
| Does it have type hints? | Better editor support and type checking |
| Is it secure? | No known unpatched vulnerabilities, sensible handling of reported issues |
| Is it replaceable? | If it is abandoned, how hard would a switch be? |

## Security of Dependencies

Installing a package runs its code on your machine, and importing it runs it in your application. Treat dependencies as part of your attack surface.

- Check the exact name before installing. Attackers publish packages with names one letter away from popular ones (typosquatting).
- Pin and hash dependencies for deployments with a lock file.
- Add as few dependencies as you reasonably can.
- Scan for known vulnerabilities regularly with a tool such as `pip-audit`.
- Never run `pip install` with `sudo` or as an administrator to fix an import error. Use a virtual environment.
- Review a new or newly updated dependency before it reaches production.

## Basic Examples

A first session using a third-party package:

```bash
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install requests
python -m pip show requests
```

```python
import requests

response = requests.get("https://example.com", timeout=5)
print(response.status_code)
print(response.headers["content-type"])
```

`timeout` is passed deliberately. Without it a request can wait indefinitely if the server never responds.

## Backend Industry Example

A project declares its dependencies in `pyproject.toml` with ranges that allow safe updates, keeps development tools separate from runtime dependencies, and commits a lock file. Continuous integration installs exactly what the lock file says and checks for known vulnerabilities.

```toml
[project]
name = "orders-service"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "requests~=2.32",
    "sqlalchemy>=2.0,<3",
    "pydantic>=2.7,<3",
]

[project.optional-dependencies]
dev = [
    "pytest>=8",
    "ruff",
    "mypy",
    "pip-audit",
]
```

Recent versions of `uv` can also store development tools in a `[dependency-groups]` table with `uv add --dev pytest`. Either approach separates what the service needs to run from what developers need to work on it.

```bash
# In continuous integration
uv sync --locked          # install exactly the locked versions, fail if the lock is stale
uv run pytest
uv run pip-audit          # report known vulnerabilities in the installed packages
```

Logging the versions of key libraries at startup makes production incidents far easier to diagnose, because the log shows what was actually running.

```python
from importlib.metadata import PackageNotFoundError, version


def dependency_versions(names: list[str]) -> dict[str, str | None]:
    """Return the installed version of each named package, or None if missing."""
    versions: dict[str, str | None] = {}
    for name in names:
        try:
            versions[name] = version(name)
        except PackageNotFoundError:
            versions[name] = None
    return versions


print(dependency_versions(["pip", "this-package-does-not-exist"]))
# {'pip': '24.0', 'this-package-does-not-exist': None}   the pip version will differ
```

`importlib.metadata` reads the metadata of installed distributions, so it reports the version that is really installed in the current environment and not the one a requirements file asked for.

## Common Mistakes

- Installing packages outside a virtual environment, or with `sudo`.
- Adding a dependency for something the standard library already does.
- Leaving versions unpinned in a deployed application so a rebuild silently pulls newer versions.
- Pinning libraries too tightly, which causes conflicts for their users.
- Not committing the lock file.
- Choosing a package only because it was the first search result, without checking maintenance and security.
- Upgrading everything at once without reading changelogs or running the tests.
- Making a typo in a package name and installing a malicious look-alike.

## Summary

PyPI is the central source of third-party packages, installed with `pip` or `uv` into a virtual environment. Use version specifiers to express which versions are acceptable and a lock file to freeze the exact versions of an application. Read documentation and changelogs, and evaluate maintenance, popularity, licensing, dependency size, and security before adopting a package. Keep dependencies few, audited, and updated on purpose.
