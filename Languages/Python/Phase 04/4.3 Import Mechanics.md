# 4.3 Import Mechanics

## Overview

An `import` statement looks simple, but Python follows a precise procedure to find, load, and cache the module. Knowing that procedure explains why a module is found or not found, why code in a module runs only once, why editing a file sometimes has no effect in a running session, and why circular imports fail.

## What Happens on import

When you write `import orders`, Python does the following:

1. It looks in `sys.modules`, a dictionary of every module already loaded. If `orders` is there, it reuses that module object and stops.
2. Otherwise it searches the directories listed in `sys.path` for a matching module or package.
3. When it finds one, it creates a new module object, stores it in `sys.modules`, and then executes the module's code from top to bottom.
4. It binds the name `orders` in the importing file to the module object.

If nothing is found, Python raises `ModuleNotFoundError`.

## sys.path

`sys.path` is the list of locations Python searches, in order.

```python
import sys

for location in sys.path:
    print(location)
```

It normally contains:

| Position | Entry |
| --- | --- |
| First | The directory of the script being run (or the current directory for `python -m` and interactive sessions) |
| Next | Directories from the `PYTHONPATH` environment variable |
| Then | The standard library directories |
| Last | `site-packages`, where installed third-party packages live (the virtual environment's `site-packages` when one is active) |

Because the script's directory comes first, a local file named `random.py` or `json.py` hides the standard library module of the same name.

You can append to `sys.path` at runtime (`sys.path.insert(0, "/some/dir")`), but this is a hack that makes code depend on where it is run. The professional solutions are to structure the project as a package and install it in editable mode, or to run it with `python -m` from the project root.

## sys.modules and Import Caching

`sys.modules` maps module names to loaded module objects.

```python
import sys

print("colorsys" in sys.modules)    # False, not imported yet
import colorsys
print("colorsys" in sys.modules)    # True

print(sys.modules["colorsys"] is colorsys)    # True: the same object
```

Consequences of the cache:

- A module's top-level code runs once per process, no matter how many files import it.
- Every importer shares the same module object and therefore the same module-level variables. A module can act as a simple shared singleton.
- Editing a module file while a program is running does not change what is already loaded. Restart the program, or in an experiment use `importlib.reload`.

```python
import importlib
import mymodule

importlib.reload(mymodule)    # runs the file again and updates the module object
```

`reload` does not update names that other files already copied with `from mymodule import name`. It is a tool for interactive work, not for production code.

## Finding Out Where Something Came From

```python
import json

print(json.__file__)       # path of the imported file
print(json.__spec__)       # how and where Python located it
```

When behaviour is surprising, check `__file__` to see whether you are importing the module you think you are. To see how long each import takes at startup, run:

```bash
python -X importtime -c "import json"
```

## Circular Imports

A circular import happens when module A imports module B and module B imports module A, directly or through a longer chain. Python starts loading A, reaches the import of B, starts loading B, and B tries to import something from A that has not been defined yet because A is still only half-executed.

```python
# shop/orders.py
from shop.customers import Customer

class Order:
    def __init__(self, order_id: str, customer: Customer) -> None:
        self.order_id = order_id
        self.customer = customer
```

```python
# shop/customers.py
from shop.orders import Order      # orders.py is already loading and imports this file

class Customer:
    def __init__(self, name: str) -> None:
        self.name = name
        self.orders: list[Order] = []
```

Importing either one fails with an error like this:

```text
ImportError: cannot import name 'Order' from partially initialized module 'shop.orders' (most likely due to a circular import)
```

The phrase "partially initialized module" is the signature of this problem.

### How to Fix Circular Imports

Fixes, in order of preference:

1. Restructure. Circular imports usually mean two modules know too much about each other. Move the shared pieces into a third module that both import, or let the dependency run in one direction only.
2. Import only for type checking. When module B needs module A only to write type hints, import it under `typing.TYPE_CHECKING`. That constant is `True` for type checkers and `False` at runtime, so the import never runs.
3. Import inside the function that needs it (a lazy import), so it happens at call time when both modules are fully loaded.
4. Import the module instead of a name: `import shop.orders` and use `shop.orders.Order` later, inside functions. The attribute is looked up at call time rather than import time.

## Lazy Imports

Importing inside a function delays the cost and the dependency until the function is used. It is also a standard way to support optional dependencies.

```python
def render_chart(data):
    # Heavy library, loaded only when a chart is actually requested
    import matplotlib.pyplot as plt
    ...
```

The usual guidance is to put imports at the top of the file, and to use a function-level import only for circular dependencies, optional packages, or rarely used heavy libraries.

## Basic Examples

```python
import sys
import math

print(sys.path[0])             # the folder of this script
print("math" in sys.modules)   # True
print(math.__file__ if hasattr(math, "__file__") else "built into the interpreter")
```

Import caching in action:

```python
# counter_module.py
print("counter_module is loading")
count = 0
```

```python
# main.py
import counter_module          # prints: counter_module is loading
import counter_module          # prints nothing, loaded once

counter_module.count += 1
import counter_module as again
print(again.count)             # 1, the same shared module object
```

## Backend Industry Example

A customer and an order that refer to each other. The order needs the customer at runtime, but the customer needs the order class only to describe a type, so that import is made type-only. A service module also imports a heavy optional library lazily.

```python
# shop/customers.py
from __future__ import annotations

from dataclasses import dataclass, field
from typing import TYPE_CHECKING

if TYPE_CHECKING:
    from shop.orders import Order      # only for type checkers, never executed


@dataclass
class Customer:
    name: str
    orders: list[Order] = field(default_factory=list)

    def lifetime_value(self) -> int:
        """Return the total of all the customer's orders, in cents."""
        return sum(order.total_cents for order in self.orders)
```

```python
# shop/orders.py
from dataclasses import dataclass

from shop.customers import Customer


@dataclass
class Order:
    order_id: str
    total_cents: int
    customer: Customer
```

`from __future__ import annotations` makes annotations plain text, so `list[Order]` does not need `Order` to exist at runtime. The dependency now points in one direction at runtime: `orders` imports `customers`, and `customers` never imports `orders` while the program runs.

```python
# run_shop.py
from shop.customers import Customer
from shop.orders import Order

amina = Customer("Amina")
amina.orders.append(Order("A-1", 12_000, amina))
amina.orders.append(Order("A-2", 3_500, amina))
print(amina.lifetime_value())    # 15500
```

A lazy import for an optional dependency, with a helpful error message:

```python
# shop/exports.py
def export_to_excel(rows: list[list[str]], path: str) -> None:
    """Write rows to an Excel file. Requires the optional openpyxl package."""
    try:
        import openpyxl
    except ImportError as exc:
        raise RuntimeError(
            "Excel export requires the 'openpyxl' package. "
            "Install it with: pip install openpyxl"
        ) from exc

    workbook = openpyxl.Workbook()
    sheet = workbook.active
    for row in rows:
        sheet.append(row)
    workbook.save(path)
```

The service starts and runs fine without `openpyxl`. Only the code path that needs it fails, and it fails with an instruction instead of a bare `ModuleNotFoundError`.

## Common Mistakes

- Naming a local file like a standard library module and shadowing it.
- Editing a module and expecting a running interpreter to pick up the change.
- Modifying `sys.path` in application code to make imports work instead of fixing the project structure.
- Creating circular imports by putting unrelated code in one module and then splitting it carelessly.
- Putting side effects such as opening a connection or reading a file at import time. They run once at first import, in an order that is hard to control.
- Hiding a circular import with a function-level import everywhere instead of fixing the design.

## Summary

An import checks `sys.modules` first, then searches `sys.path`, executes the module once, and caches it. Because of the cache, module-level code runs once and the module object is shared. Circular imports appear as "partially initialized module" errors. Fix them by restructuring, by using `TYPE_CHECKING` for type-only imports, or with a lazy import. Keep `sys.path` untouched and rely on proper packaging and `python -m` instead.
