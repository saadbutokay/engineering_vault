# 1.7 Reading Errors

## Overview

Errors are normal. The difference between a beginner and an experienced developer is how quickly each reads the error message and finds the cause. Python error messages are detailed and usually tell you exactly what went wrong and where.

## Anatomy of a Traceback

When an exception is not handled, Python prints a traceback. Consider this file named `report.py`:

```python
def average(numbers):
    return sum(numbers) / len(numbers)


def report(scores):
    mean = average(scores)
    print(f"Average: {mean}")


report([])
```

Running it prints:

```text
Traceback (most recent call last):
  File "report.py", line 10, in <module>
    report([])
  File "report.py", line 6, in report
    mean = average(scores)
  File "report.py", line 2, in average
    return sum(numbers) / len(numbers)
ZeroDivisionError: division by zero
```

How to read it:

1. The first line announces a traceback and tells you the order: the most recent call is last.
2. Each pair of lines is a stack frame: the file and line number, the function name, and the source line being executed. Reading from top to bottom follows the chain of calls from where the program started to where the failure happened.
3. The last line is the exception type and its message. Start reading here.
4. The last frame is where the exception was raised. The frame above it shows who called that code. The real cause is sometimes in a caller, for example the code that passed an empty list.

Newer Python versions also print marker characters under the exact part of the line that failed, which narrows the problem further.

## Common Exceptions

### SyntaxError

The code is not valid Python. It is reported before the program runs, with the location of the problem.

```python
print("hello"
```

```text
SyntaxError: '(' was never closed
```

Common causes: missing closing bracket or quote, missing colon after `if` or `def`, using `=` where `==` is needed. The real mistake is sometimes on the line before the one reported. `IndentationError` is a kind of `SyntaxError` for wrong indentation.

### NameError

A name was used before it was defined, or it was misspelled.

```python
total = 10
print(totl)
```

```text
NameError: name 'totl' is not defined. Did you mean: 'total'?
```

### TypeError

An operation was applied to the wrong type, or a function got the wrong arguments.

```python
print("Age: " + 30)
```

```text
TypeError: can only concatenate str (not "int") to str
```

Other common forms: `'NoneType' object is not subscriptable` (you used `[]` on `None`, usually because a function returned nothing) and `add() takes 2 positional arguments but 3 were given`.

### ValueError

The type is right but the value is not acceptable.

```python
int("abc")
```

```text
ValueError: invalid literal for int() with base 10: 'abc'
```

### IndexError

A sequence position does not exist.

```python
items = [1, 2, 3]
print(items[5])
```

```text
IndexError: list index out of range
```

### KeyError

A dictionary key does not exist.

```python
user = {"name": "Amina"}
print(user["email"])
```

```text
KeyError: 'email'
```

### Others You Will Meet Often

| Exception | Typical cause |
| --- | --- |
| `AttributeError` | `'str' object has no attribute 'push'`: calling a method that does not exist on that type, often on `None` |
| `ZeroDivisionError` | dividing by zero |
| `ModuleNotFoundError` | package not installed in the active environment, or wrong interpreter |
| `FileNotFoundError` | wrong path or wrong working directory |

## A Systematic Way to Debug a Failing Script

1. Read the last line of the traceback. Note the exception type and message.
2. Find the deepest frame that is in your own code, not in a library, and go to that file and line.
3. Look at the values involved. Add a temporary `print(repr(value))` or set a breakpoint and inspect them.
4. Ask which assumption is false: the value is `None`, empty, the wrong type, or has a different shape than expected.
5. If the bad value came from a caller, move up one frame and repeat.
6. Reproduce the failure with the smallest possible input.
7. Change one thing at a time, then run again.
8. Search for the exact error message text (without your own file names and values) if the cause is still unclear.

Avoid changing code at random until the error disappears. A fix you cannot explain usually comes back as another bug.

## Basic Examples

Finding the cause using the steps above:

```python
def get_discount(user):
    return user["discount"]


users = [{"name": "Amina", "discount": 0.1}, {"name": "Bilal"}]
for user in users:
    print(get_discount(user))
```

The traceback ends with `KeyError: 'discount'`. The failing line is `return user["discount"]`. Printing `user` at that point shows `{'name': 'Bilal'}`, so the second user has no `discount` key. The bug is in the data, and the fix is either to supply the value or to read it with a default: `user.get("discount", 0)`.

## Backend Industry Example

A webhook handler fails in production with this traceback:

```python
def parse_order(payload):
    return payload["order_id"], int(payload["quantity"])


parse_order({"order_id": "A-1001"})
```

```text
Traceback (most recent call last):
  File "webhook.py", line 5, in <module>
    parse_order({"order_id": "A-1001"})
  File "webhook.py", line 2, in parse_order
    return payload["order_id"], int(payload["quantity"])
KeyError: 'quantity'
```

The error is accurate, but a bare `KeyError: 'quantity'` in a log tells an on-call engineer little. Professional code catches expected failures at the boundary, adds context, and records the full traceback.

```python
import logging

logger = logging.getLogger(__name__)


def parse_order(payload: dict) -> tuple[str, int]:
    """Extract the order id and quantity from a webhook payload."""
    try:
        return payload["order_id"], int(payload["quantity"])
    except KeyError as exc:
        raise ValueError(f"Missing field in order payload: {exc}") from exc
    except (TypeError, ValueError) as exc:
        quantity = payload.get("quantity")
        raise ValueError(f"Invalid quantity in order payload: {quantity!r}") from exc


def handle_webhook(payload: dict) -> int:
    """Return an HTTP status code for the webhook request."""
    try:
        order_id, quantity = parse_order(payload)
    except ValueError:
        logger.exception("Rejected webhook payload")
        return 400
    logger.info("Accepted order %s with quantity %s", order_id, quantity)
    return 202
```

The `try` and `except` blocks catch an error and replace it with a clearer one. `raise ... from exc` keeps the original error attached. `logger.exception` records the message together with the full traceback. The client receives status `400` because the input was bad, instead of a generic `500` for a crash. The reading skills in this note still apply: when this code fails, the log contains a traceback in exactly the same format.

## Common Mistakes

- Reading from the top of the traceback and ignoring the last line.
- Looking only at the line where the error is shown, when the bad value was created earlier or in a caller.
- Blaming the library when the failing frame is in your own code.
- Hiding errors with a bare `except:` or `except Exception: pass`, which removes the information needed to debug.
- Editing several things at once, so it is unclear which change fixed or broke anything.
- Pasting only the last line when asking for help instead of the whole traceback and the code that produced it.

## Summary

Read tracebacks from the bottom: the last line names the exception, and the frames above show how the program got there. Learn the common exceptions and what each usually means. Debug systematically by finding the failing line in your code, inspecting the values, identifying the false assumption, reproducing with minimal input, and changing one thing at a time. In production, log the full traceback and turn expected failures into clear messages.
