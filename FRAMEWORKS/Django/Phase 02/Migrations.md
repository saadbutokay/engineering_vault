## Overview

Migrations are Django's version control for your database schema. Each migration is a Python file that describes one step in moving the schema from one state to the next, such as creating a table, adding a column, or adding an index. Because they are code, they are committed to Git, reviewed, tested, and applied identically on every developer's machine and on every server. This note covers the migration commands, how the migration graph works, how to read a migration file, data migrations with `RunPython` and `RunSQL`, reversibility, squashing, merge migrations, and the rule that applied migrations are never edited. It ends with a three-step, tested migration that safely adds a required, unique column to a table that already contains data.

## Core concepts

### The commands

- `makemigrations`: compare your models with the migration history and write new migration files.
- `migrate`: apply unapplied migrations to the database.
- `sqlmigrate app 0001`: print the SQL a migration will run, without running it.
- `showmigrations`: list migrations and whether they are applied.
- `makemigrations --check --dry-run`: exit with an error if models changed without a migration. Use it in CI.

### What a migration file contains

- `dependencies`: the migrations that must be applied first.
- `operations`: an ordered list of steps such as `CreateModel`, `AddField`, `AlterField`, `RemoveField`, `AddIndex`, `AddConstraint`, `RunPython`, and `RunSQL`.
- `initial = True` on the first migration of an app.

### The migration graph

Migrations form a directed graph through their dependencies. Normally it is a straight line (`0001`, `0002`, `0003`), and Django records which have run in the `django_migrations` table. The newest migration in a line is a leaf node. Two leaf nodes in one app mean the history has forked, which `migrate` refuses to apply until you merge it.

### Data migrations

`RunPython(forwards, backwards)` runs Python functions, and `RunSQL(sql, reverse_sql)` runs SQL. Use them to backfill or transform existing data when the schema changes.

### Reversible migrations

A migration is reversible if every operation can be undone. Schema operations are reversible automatically. For `RunPython` and `RunSQL` you supply the reverse step, or pass `migrations.RunPython.noop` and `migrations.RunSQL.noop` when undoing needs no action. Reversibility lets you roll back a bad deploy.

### Squashing

`squashmigrations` combines a run of migrations into one equivalent migration to shorten long histories and speed up creating a fresh database.

### Merge migrations

When two branches each add a migration to the same app, the graph forks. `makemigrations --merge` creates a migration that depends on both leaves and joins the history.

### Why migration files are committed

They are the shared definition of how the schema evolves. Every environment, from a new teammate's laptop to production, replays the same history. Ignoring them in Git (note 0.8) breaks that guarantee.

### Never edit an applied migration

Once a migration has been applied anywhere beyond your own machine, treat it as immutable. Editing it does not change databases that already ran it, so environments drift apart. Add a new migration instead.

## Basic syntax examples

### The everyday cycle

```bash
uv run python manage.py makemigrations
uv run python manage.py makemigrations bookstore --name add_author_slug
uv run python manage.py migrate
uv run python manage.py showmigrations bookstore
```

### Inspecting the SQL

```bash
uv run python manage.py sqlmigrate bookstore 0001
```

```sql
BEGIN;
--
-- Create model Author
--
CREATE TABLE "bookstore_author" (
    "id" bigint NOT NULL PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY,
    "name" varchar(200) NOT NULL,
    "born_on" date NULL,
    "created_at" timestamp with time zone NOT NULL
);
COMMIT;
```

Reading the SQL before you apply a migration to production is a good habit, especially for changes on large tables.

### Anatomy of a migration

```python
from django.db import migrations, models


class Migration(migrations.Migration):
    initial = True

    dependencies = []

    operations = [
        migrations.CreateModel(
            name="Author",
            fields=[
                (
                    "id",
                    models.BigAutoField(
                        auto_created=True,
                        primary_key=True,
                        serialize=False,
                        verbose_name="ID",
                    ),
                ),
                ("name", models.CharField(max_length=200)),
            ],
        ),
    ]
```

### Moving backward

```bash
uv run python manage.py migrate bookstore 0001     # undo everything after 0001
uv run python manage.py migrate bookstore zero     # undo all of the app's migrations
```

### An empty migration for hand-written steps

```bash
uv run python manage.py makemigrations bookstore --empty --name backfill_example
```

### RunSQL

```python
from django.db import migrations


class Migration(migrations.Migration):
    dependencies = [("bookstore", "0001_initial")]

    operations = [
        migrations.RunSQL(
            sql="UPDATE bookstore_book SET stock = 0 WHERE stock < 0;",
            reverse_sql=migrations.RunSQL.noop,
        ),
    ]
```

### RunPython

```python
from django.apps.registry import Apps
from django.db import migrations
from django.db.backends.base.schema import BaseDatabaseSchemaEditor


def clean_names(apps: Apps, schema_editor: BaseDatabaseSchemaEditor) -> None:
    Author = apps.get_model("bookstore", "Author")
    for author in Author.objects.all():
        author.name = " ".join(author.name.split())
        author.save(update_fields=["name"])


class Migration(migrations.Migration):
    dependencies = [("bookstore", "0001_initial")]

    operations = [
        migrations.RunPython(clean_names, migrations.RunPython.noop),
    ]
```

### Fixing a forked graph

```bash
uv run python manage.py makemigrations --merge
```

### Squashing

```bash
uv run python manage.py squashmigrations bookstore 0001 0005
```

### Checking in CI

```bash
uv run python manage.py makemigrations --check --dry-run
```

## Deeper behavior

### Historical models in RunPython

Inside a migration you must get models with `apps.get_model("app", "Model")`, not by importing them. This returns the model as it existed at that point in history, matching the schema at that step. The historical model has the fields but not your custom methods, properties, or managers (unless a manager sets `use_in_migrations = True`). Importing the real model would break the migration as soon as the model changes later.

### How Django decides what changed

`makemigrations` loads the state built from all existing migrations, compares it with the current models, and writes the difference. Renaming a field looks like a removal plus an addition, so Django asks whether you renamed it. Answer yes to keep the data. For anything else it cannot infer, write the migration by hand.

### Adding a required column to a populated table

Adding `NOT NULL` without a default fails when rows already exist. The safe sequence, which the industry example implements, is:

1. Add the column as nullable.
2. Backfill existing rows in a data migration.
3. Alter the column to `NOT NULL` and add `unique` or other constraints.

Splitting these into separate migrations also avoids mixing schema changes and data changes in one transaction.

### Transactions and DDL

On PostgreSQL, each migration runs in a transaction, and schema changes roll back with it. On SQLite, Django remakes the table for many alterations. Mixing large data updates and schema changes in one transaction on PostgreSQL can fail with "pending trigger events" errors, another reason to separate them. A migration class can set `atomic = False` for steps that must not run in a transaction, such as `CREATE INDEX CONCURRENTLY` (Phase 11).

### Locks and large tables

Some schema changes lock the table while they run. Adding an index or a constraint to a big table in production can block writes for a long time. Note 12.5 covers lock-aware patterns such as expand and contract. For now, read `sqlmigrate` output and know which operations are expensive.

### Faking migrations

`migrate --fake` records a migration as applied without running it. It is a repair tool for when the database already matches the migration. Using it casually creates the drift migrations are meant to prevent.

### Squashing safely

A squashed migration lists the migrations it replaces. Django uses the squash for fresh databases and the originals for databases partway through the history. Delete the originals only after every environment has applied them, and update dependencies in other apps.

### Migration conflicts after a merge

If `makemigrations --merge` reports conflicting leaves, check that the two migrations do not touch the same fields in incompatible ways. If they do, the safer fix is to delete your unshared migration, merge the other branch, and regenerate yours so it depends on the latest one (note 0.8).

### Naming

Give descriptive names with `--name`. A history with `0007_add_author_slug` is far easier to review than `0007_auto_20260314_1022`.

## Industry-level snippet

The most common real migration task: adding a required, unique `slug` to `Author` when authors already exist. Three migrations implement expand, backfill, and contract. The slug logic is a pure function, tested directly, and the data migration is tested by migrating a real database to the step before and after it.

First update the model, then generate the first migration:

```python
# apps/bookstore/models.py (Author)
slug = models.SlugField(max_length=220, null=True, blank=True)
```

`apps/bookstore/migrations/0002_author_slug.py`:

```python
from django.db import migrations, models


class Migration(migrations.Migration):
    dependencies = [("bookstore", "0001_initial")]

    operations = [
        migrations.AddField(
            model_name="author",
            name="slug",
            field=models.SlugField(blank=True, max_length=220, null=True),
        ),
    ]
```

`apps/bookstore/migrations/0003_populate_author_slugs.py`:

```python
from collections.abc import Iterable

from django.apps.registry import Apps
from django.db import migrations
from django.db.backends.base.schema import BaseDatabaseSchemaEditor
from django.utils.text import slugify

BATCH_SIZE = 500


def assign_slugs(rows: Iterable[tuple[int, str]]) -> dict[int, str]:
    """Return a unique slug for each ``(pk, name)`` pair.

    Names that produce the same slug get ``-2``, ``-3``, and so on. A name
    that produces an empty slug falls back to ``author-<pk>``.
    """
    used: set[str] = set()
    result: dict[int, str] = {}
    for pk, name in rows:
        base = slugify(name)[:200] or f"author-{pk}"
        slug = base
        suffix = 2
        while slug in used:
            slug = f"{base}-{suffix}"
            suffix += 1
        used.add(slug)
        result[pk] = slug
    return result


def populate_slugs(apps: Apps, schema_editor: BaseDatabaseSchemaEditor) -> None:
    Author = apps.get_model("bookstore", "Author")
    authors = list(Author.objects.order_by("pk"))
    slugs = assign_slugs((author.pk, author.name) for author in authors)
    for author in authors:
        author.slug = slugs[author.pk]
    Author.objects.bulk_update(authors, ["slug"], batch_size=BATCH_SIZE)


class Migration(migrations.Migration):
    dependencies = [("bookstore", "0002_author_slug")]

    operations = [
        migrations.RunPython(populate_slugs, migrations.RunPython.noop),
    ]
```

This version loads all authors into memory, which is fine for thousands of rows. For millions, iterate in chunks with `iterator(chunk_size=...)` and update per chunk.

`apps/bookstore/migrations/0004_author_slug_unique.py`:

```python
from django.db import migrations, models


class Migration(migrations.Migration):
    dependencies = [("bookstore", "0003_populate_author_slugs")]

    operations = [
        migrations.AlterField(
            model_name="author",
            name="slug",
            field=models.SlugField(max_length=220, unique=True),
        ),
    ]
```

After this migration, change the model to `slug = models.SlugField(max_length=220, unique=True)` so the model and history agree, and make sure new authors receive a slug when they are created (exercise 3).

`apps/bookstore/tests/test_slug_migration.py`:

```python
import importlib
from typing import Any

from django.core.management import call_command
from django.db import connection
from django.db.migrations.executor import MigrationExecutor
from django.test import SimpleTestCase, TransactionTestCase

slug_migration: Any = importlib.import_module(
    "apps.bookstore.migrations.0003_populate_author_slugs"
)


class AssignSlugsTests(SimpleTestCase):
    def test_slugs_are_derived_from_names(self) -> None:
        result = slug_migration.assign_slugs([(1, "Ada Lovelace")])
        self.assertEqual(result, {1: "ada-lovelace"})

    def test_duplicates_get_numeric_suffixes(self) -> None:
        result = slug_migration.assign_slugs(
            [(1, "Ada Lovelace"), (2, "ada  lovelace"), (3, "ADA LOVELACE")]
        )
        self.assertEqual(
            result, {1: "ada-lovelace", 2: "ada-lovelace-2", 3: "ada-lovelace-3"}
        )

    def test_empty_slug_falls_back_to_the_primary_key(self) -> None:
        result = slug_migration.assign_slugs([(7, "!!!")])
        self.assertEqual(result, {7: "author-7"})


class PopulateAuthorSlugsMigrationTests(TransactionTestCase):
    before = [("bookstore", "0002_author_slug")]
    after = [("bookstore", "0003_populate_author_slugs")]

    def setUp(self) -> None:
        super().setUp()
        executor = MigrationExecutor(connection)
        executor.migrate(self.before)
        old_apps = executor.loader.project_state(self.before).apps
        old_author = old_apps.get_model("bookstore", "Author")
        self.pks = [
            old_author._default_manager.create(name=name).pk
            for name in ("Ada Lovelace", "ada lovelace", "!!!")
        ]

        executor = MigrationExecutor(connection)
        executor.migrate(self.after)
        self.new_apps = executor.loader.project_state(self.after).apps

    def tearDown(self) -> None:
        call_command("migrate", verbosity=0)
        super().tearDown()

    def test_every_author_receives_a_unique_slug(self) -> None:
        new_author = self.new_apps.get_model("bookstore", "Author")
        slugs = {
            author.pk: author.slug for author in new_author._default_manager.all()
        }
        self.assertEqual(
            slugs,
            {
                self.pks[0]: "ada-lovelace",
                self.pks[1]: "ada-lovelace-2",
                self.pks[2]: f"author-{self.pks[2]}",
            },
        )
```

The tests demonstrate the real discipline of migrations: pure logic is extracted and tested quickly, and the data step is exercised against a database in the exact state it will meet in production.

## Common mistakes

- Editing a migration that has already been applied elsewhere.
- Deleting migration files to "fix" an error, which breaks every database that already ran them.
- Adding a `NOT NULL` column without a default to a table that has rows.
- Importing models directly in `RunPython` instead of using `apps.get_model`.
- Calling model methods or relying on custom managers inside migrations, which historical models lack.
- Mixing a large data update and schema changes in a single migration on PostgreSQL.
- Writing a `RunPython` with no reverse function, which makes the migration irreversible and blocks rollbacks.
- Forgetting `makemigrations --check` in CI, so a missing migration is discovered in production.
- Using `--fake` to silence an error without understanding why the state disagreed.
- Ignoring `sqlmigrate` and applying an expensive lock-taking migration to a busy production table.
- Leaving auto-generated, meaningless migration names.

## Summary

Migrations record every schema change as an ordered, committed, reviewable Python file, applied with `migrate` and previewed with `sqlmigrate`. The migration graph defines the order, and forks are repaired with merge migrations. `RunPython` and `RunSQL` handle data changes, and they should be reversible and use historical models. Applied migrations are never edited. Adding a required column to a populated table takes three steps: add it as nullable, backfill, then tighten it. Check in CI that models and migrations agree, read the SQL before applying risky changes, and test data migrations against real databases.
